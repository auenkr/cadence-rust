# Frontend Admin replication: implementation decisions

2026-11-01; research against integrated audit `60fa3b657` and current branch. This is authorization to extend cadence-api and Thrift models/converters as necessary for complete parity; those extensions are already implied by the task. Do not ship partial task data or fabricated empty success. No implementation or validation was performed here.

## Ownership and live path

`cadence-matching/src/launcher.rs:836,1106,1923-1938` configures a lazy `AppState.history_admin_channel`, clones state, and launches `grpc::serve`. `cadence-matching/src/grpc.rs:2144` registers `grpc_admin::Admin`; it is live, not an alternative to service-core. `cadence-service-core/src/handlers.rs:1480` registers `yarpc_handler`, while `admin.rs:687-708` supplies JSON endpoints. The two gRPC stubs (`grpc_admin.rs:838-860`), JSON stubs, and missing YARPC arms must all change.

Put the transport-independent validation/History calls in a public service-core module (e.g. `admin_replication.rs`) accepting internal History protobuf requests and returning internal History protobuf responses plus a typed error. Call it directly from gRPC and from JSON/YARPC adapters. Protobuf internal History and public Admin response fields use the *same* `admin.v1.ReplicationMessages`/`ReplicationTask` messages (`go/proto/internal/uber/cadence/history/v1/service.proto:637-652`, `go/idls/proto/uber/cadence/admin/v1/service.proto:259-275`): gRPC can move the maps/vectors directly, without a lossy model round-trip. JSON/YARPC convert at their boundaries. `cadence-frontend` depends on service-core, so service-core must not depend on frontend; its existing `handler_admin_history.rs:98-130` and `history_client.rs:360-390` are useful references, not the production shared owner. Its DLQ method currently misses empty-list validation and maps all statuses to internal; fix if reused. Matching already depends on service-core and proto, so this direction has no cycle.

`history_admin_channel` is one configured host, not a multi-host routed History client. Introduce a service-core injectable History routing interface implemented/wired at the launcher, reusing or adapting `cadence-matching/src/matching_history_peer_resolver.rs` and membership; do not depend on Matching from service-core. Keep configured single-host channel as explicit single-host case, not proof of multi-host parity. Preserve request metadata/deadline and use `admin.rs:1421`'s existing History metadata convention as applicable. No endpoint should silently fall back to an empty result when History or routing is unavailable.

## Wire model and conversion checklist

Source of truth: `go/idls/thrift/replicator.thrift:25-170`, `admin.thrift:102-126`, `history.thrift:947-970`, protobuf `admin/v1/replication.proto:32-149` and `admin/v1/history.proto:27-39`. Extend `cadence-api/src/admin.rs` with `GetReplicationMessagesResponse` (Thrift field 10 map i32 to `ReplicationMessages`; proto `shard_messages`) and `GetDLQReplicationMessagesResponse` (field 10 task list). Extend existing `ReplicationMessages` with optional sync shard status timestamp (field 40), preserving task list 10, last retrieved 20, has more 30. Complete `ReplicationTaskInfo` request: domain, workflow ID, run ID, i16 task type, task ID, version, first event ID, **next event ID and scheduled ID** (Thrift fields 10 through 90 by tens); proto nests workflow/run in `workflow_execution` and uses i32 task type. Preserve safe range/presence per Go mapper, and full token fields.

Extend `cadence-api/src/types.rs` `ReplicationTask`: type field 10, source ID 11, domain attributes 20, sync shard 40, sync activity 50, history V2 70, failover marker 80, creation time 90. Thrift is a struct with independently optional attributes; proto is a oneof at fields 4-8. Preserve all fields representable by the source format; do not silently select one if an invalid multi-attribute Thrift input is encountered. Pinned enums include Domain, History, SyncShardStatus, SyncActivity, HistoryMetadata, HistoryV2, FailoverMarker; protobuf reserves zero INVALID and offsets the Thrift enum by one.

Each pinned attribute, including nested values:

* Domain: operation, ID, DomainInfo, DomainConfiguration, DomainReplicationConfiguration, config/failover/previous failover versions. Proto combines info/config/replication configuration in `api.v1.Domain`. Verify against `go/common/types/mapper/{proto,thrift}/replicator.go`; notably pinned Thrift `DomainTaskAttributes` uses IDs **5,10,20,30,40,50,60,70**, whereas existing `cadence-thrift/src/convert.rs:1435` uses 10,20,...80: reconcile carefully with actual generated wire and tests, not the existing self-roundtrip.
* SyncShardStatus: source cluster, shard ID (Thrift i64 versus proto i32), timestamp.
* SyncActivity: domain/workflow/run IDs, version, scheduled ID/time, started ID/time, last heartbeat time, details bytes, attempt, last failure reason/details/options, last worker identity, version history (branch token and event ID/version items). Proto groups IDs in WorkflowExecution, details in Payload, failure fields in Failure.
* HistoryV2: task ID, domain/workflow/run IDs, version history items (event ID/version), events and new-run-events DataBlob including encoding and bytes.
* FailoverMarker: domain ID, failover version, creation time. Task envelope creation time and sync status timestamps must survive too. Compare Go proto mapper's exact time units (`go/common/types/mapper/proto/replicator.go`) and use nanosecond-safe conversions, retaining optional values as far as the respective wire permits.

Implement request decoding and response encoding in `cadence-thrift/src/convert.rs`, both directions where supported, with exact Thrift field IDs/types and map handling; register `GetReplicationMessages`/`GetDLQReplicationMessages` arms in `cadence-service-core/src/yarpc.rs` using `service.rs:969-1000` method exception tables. Add protobuf <-> API replication converters in `cadence-proto/src/convert` (which already depends on API), shared by JSON/YARPC; use existing `execution`, `execution_out`, `version_history_out`, `timestamp_nanos`, `failure_in` and enum helpers only after checking presence, units, and round-trip fidelity. In particular `payload` drops empty bytes and `grpc_admin.rs`'s `data_blob_out` forces JSON: neither is safe as a general lossless replication converter. Extend helpers as needed; avoid saturating or narrowing values silently. Go Thrift mapper and generated schema govern binary field IDs, not an API-only round trip.

## Semantics and routing

Go `service/frontend/admin/handler.go:920-943,1003-1029`: nil request => BadRequest `Request is nil.`; replication empty cluster => `Cluster name is not set.`; DLQ empty taskInfos => `Replication task info is not set.` Validate in that order before touching History. Go passes the original request, and `adh.error` maps the History errors; preserve declared Admin exception distinctions and gRPC status/details, rather than coercing every History status to internal. Missing/malformed Thrift argument must be distinguishable from an empty decoded struct; gRPC normally cannot express nil body and JSON null should be handled consistently.

Crucial: raw means **without retry**, not without routing. `go/common/resource/resource_impl.go:288-300,604-610`: raw is the History client, while normal wraps it with History retry policy. The raw `GetReplicationMessages` implementation (`go/client/history/client.go:729-793,796-859`) resolves each token's shard owner, groups by peer, sends concurrently with child contexts, merges using Go's size/earliest-creation ordering and limit, propagates ServiceBusy but fails open for other per-peer errors; resolver failures propagate. No tokens yields empty aggregation without an RPC. Reproduce this behavior and its response-size policy, not just direct forwarding to one host. DLQ (`client.go:881-899`) routes using the first task's workflow ID (all tasks are expected in the same shard) and uses the retry-wrapped client, preserving Go retry policy/error classification and context. Do not fan out DLQ or add validation that Go does not perform. Existing single-channel frontend helper does neither multi-peer routing nor retries. Config/discovery and response-size information may require additional integration; record any actual missing mechanism rather than claiming parity from single-host tests.
