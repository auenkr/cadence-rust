# Frontend transport follow-ups from master source audit

Audited master source after synchronization, 2026-11-01. These are implementation tasks, not completed behavior or test evidence. Two active Luna workers already own replication wire fixtures and Ringpop lifecycle; do not exceed two workers to start these.

## Next bounded workflow adapter slices

1. gRPC asynchronous start adapters: `cadence-matching/src/grpc.rs` `start_workflow_execution_async` and `signal_with_start_workflow_execution_async` directly enqueue into the local execution store. Route both through installed WorkflowApi when served, preserving original caller metadata/deadline and existing protobuf wrapper validation. Follow the tested synchronous hook adapter pattern, preserve the no-hook runtime fallback, and verify shared handler feature/config gates. Test routing, missing nested request, error identity, headers/deadline and no local enqueue under hook.
2. gRPC history: `get_workflow_execution_history` directly calls local `history_page`, forces empty raw_history and uses a fixed 60-second wait deadline. Adapt to the shared Frontend history operation; preserve filters, tokens, raw blobs, archival flag and inbound deadline/cancellation. Compare the Go handler's wait/continuation rules and shared history implementation before claiming parity. Independent fixtures must exercise pagination, raw history and close-event long polls.
3. gRPC visibility: list-open/list-closed call `visible` and local filtering/pagination, while list-archived returns a fixed cluster-not-configured error. Route through shared operations and real configured visibility backends, preserving oneof filters, enum mapping, query/error semantics and pagination. Backend parity is independently required; routing alone does not establish advanced/archival support.
4. HTTP workflow routing: launcher constructs `handlers::router(state.clone())` before installing WorkflowApi only in gRPC/TChannel clones. HTTP `start_workflow` and `signal_with_start_workflow` directly invoke execution-store operations and do not read the hook. Both installation order and actual handler dispatch need changes; installing a hook in router state alone is insufficient. Cover all public HTTP workflow routes and direct `/yarpc` access, metadata/deadline policy, feature/config gates and shared error mapping. Coordinate launcher edits with the Ringpop worker rather than overlap them.

The gRPC `Frontend::call` helper already checks the hook through its HTTP-path mapping. Methods that use that helper must be inspected separately; do not infer they bypass the hook merely because they reference HTTP paths. The direct implementations listed above were read explicitly. Likewise, the WorkflowApi module's broad introductory claim that transports route every operation through it is not completion evidence.

Validation remains GitHub Actions only, followed by mixed Rust Frontend+Matching / Go History+Worker tests and restart/failure evidence. Do not run Cargo, rustfmt or Go validation locally.
