## Async production dependency audit (continuation)

The async adapter task has an additional production prerequisite. `handler_workflow.rs` stores an optional `AsyncWorkflowPublisher`; its dispatch branch publishes the Go-compatible ThriftRW envelope only when that publisher is installed. A repository-wide source search found `with_async_publisher` used only by the handler's test. `workflow_backend.rs::build_workflow_api` constructs the production handler with domain lookup, quotas, authorization and version checking but no async publisher. Therefore hooking the gRPC methods into this handler cannot by itself establish asynchronous API parity.

Go references: `go/service/frontend/api/handler.go::StartWorkflowExecutionAsync` (around 1601) and `SignalWithStartWorkflowExecutionAsync` (around 2216). Both validate before selecting a producer by domain, serialize the complete request using ThriftRW, propagate original caller headers, set the workflow ID partition key and request type, then return success only after `producer.Publish` succeeds. Preserve producer selection/configuration errors and publish errors. `handler_workflow_async.rs` already encodes the envelope, but its unit tests do not prove that the production publisher is configured or durable.

- Adapter worker: add the two async routes to `grpc.rs::hook_operation`, pass the public API wrapper `{request: ...}` through the shared hook before touching the local execution store, and retain the existing no-hook fallback. Extend `workflow_hook_tests::RecordingApi` to exercise both operations, missing wrappers, caller metadata/deadline, success and error, including evidence that the local queue was not used. Validate `cadence-matching` via CI. This worker owns grpc.rs only and must describe its result as transport routing.
- Publisher worker: port Go's domain-specific producer manager/configuration and production publisher installation. First inspect existing persistence/queue support and Go producer manager; implement the Go-supported configured modes and failure semantics without substituting a local in-memory enqueue. Add injectable producer tests for selection, full wire payload, headers, persistence acknowledgement and errors, then use a Go Worker mixed fixture to prove consumption. Keep this within Frontend dependencies; do not start a Worker migration.

## Confirmed configured visibility pool bug and assignment

`matching_task_store.rs` builds SQL `ConfiguredMatchingStores` from `persistence.defaultStore` and sets both `history_node_store` and `visibility_store` to that same task-store instance (MySQL around 335, PostgreSQL around 399). Launcher then copies this visibility store into Frontend state around 1544; `build_workflow_api` passes it to ProductionBackend. This bypasses the already existing `PersistenceStoreRole::Visibility` selector. The mixed lane explicitly uses `cadence` as default and `cadence_visibility` for visibility, so list operations address the wrong database. Both SQL visibility adapters query `executions_visibility` through their task store's pool. This is a source-confirmed configuration bug, independent of the running gate's pending result.

Normal `MySqlTaskStore::connect` is not a visibility-only constructor: `connect_with_pools` invokes `validate_schema()` for task tables. Opening that normal task store against the visibility-only schema would introduce a different failure. The required fix is a visibility-only pool/reader constructor or equivalent, selecting configured visibility SQL credentials/database/address/TLS/limits, with no task schema validation or schema installation. History/task/domain readers stay on defaultStore; Matching-only startup must not acquire a new visibility dependency. Same-store sharing should follow configured manager roles rather than being assumed.
