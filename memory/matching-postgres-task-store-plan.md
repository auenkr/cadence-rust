# Matching PostgreSQL task-store parity plan

## Go behavior audited

- Go's PostgreSQL plugin uses the same SQL `sqlTaskStore` operation layer as MySQL and SQLite, with PostgreSQL-specific statements and `schema/postgres/cadence/schema.sql`.
- The PostgreSQL `task_lists` primary key is `(shard_id, domain_id, name, task_type)`; `tasks` is keyed by `(domain_id, task_list_name, task_type, task_id)` and has no shard column. Both tables store Cadence blobs in `BYTEA` plus `data_encoding`.
- `GetDBShardIDFromDomainIDAndTasklist` is FarmHash32 over the canonical domain UUID text, underscore, and task-list name, modulo configured database shard count. The same shard's connection is used for the SQL transaction; its shard ID is stored in `task_lists`.
- Go's sharded SQL config requires `NumShards > 1` and exactly that many `MultipleDatabasesConfig` entries. A single database uses one connection. The PostgreSQL plugin configures each database/sql pool from `MaxConns`, positive `MaxIdleConns`, and positive `MaxConnLifetime`; database/sql's default idle cap is two.
- `LeaseTaskList` selects first, inserts a missing range-zero task-list row outside the transaction, then starts a transaction, `SELECT ... FOR UPDATE`s the row, compares the old range, increments and updates it. A missing-row race can therefore surface a duplicate-key persistence error. `UpdateTaskList` similarly locks and range-checks inside a transaction. `CreateTasks` inserts task rows and locks/checks the task-list lease in one transaction so a stale range rolls task inserts back.
- Task reads use the exclusive lower bound `(read_level, max_read_level]`, ascending task IDs, and SQL `LIMIT`. Size counts `task_id > ack_level`. Single completion ignores affected-row count; limited completion deletes rows at or below the inclusive ID in ascending key order and returns affected count. Task-list delete is range-fenced and requires exactly one row.
- PostgreSQL does not support the Go SQL TTL plugin operations; expiry and creation timestamps remain in Go Thrift blobs. Shared Rust `matching_blob` codecs preserve those blob shapes and encoding labels. Go `ConnectAttributes` are added as PostgreSQL URL parameters. TLS is off by default; enabled TLS defaults to `sslmode=require` and may carry `sslrootcert`, `sslcert`, and `sslkey`.
- PostgreSQL driver SQLSTATEs distinguish query cancellation (`57014`), connection/resource throttling (`53300`, `53000`), unique violations (`23505`), and ordinary server failures. Go marks context deadline errors as timeout and server resource-limit codes as throttling.
- Go's Matching task persistence callsites pass `context.Background()` into `sqlTaskStore`; the Postgres plugin itself only receives `connect_timeout` when configured through `ConnectAttributes`. The current Rust `MatchingTaskStore` interface has no operation context, so this adapter does not invent per-query deadlines. PostgreSQL query timeout compatibility remains a runtime/interface concern if callsites later propagate request deadlines.
- PostgreSQL domain metadata uses the default domain shard `54321`: `domains` stores UUIDs as 16-byte `BYTEA`, name, global flag and ThriftRW/Snappy blob plus encoding; `domain_metadata` is a singleton notification-version table. Go selects and pages by raw UUID bytes (`id > token ORDER BY id LIMIT size`) and returns the final UUID when a page is full. The shared Rust domain decoder already accepts the same opaque Go blob encodings, but there is no PostgreSQL reader yet.

## Bounded Rust implementation slice

Implement a separate `PostgresTaskStore` implementing the existing `MatchingTaskStore` trait, using a PostgreSQL connection pool, one pool per configured physical DB shard, the repository's shared blob codecs, and the Go FarmHash routing rule. Cover schema validation, metadata read, lease/update fencing, atomic task creation, bounded reads/counts, completion, GC, and range-fenced task-list deletion. Use a typed connection config with per-shard address/database credentials plus the Go pool limits and recognized PostgreSQL timeout/TLS attributes. Fail closed on unsupported transport/TLS configuration rather than silently disabling it.

The current source slice adds `PostgresTaskStore` with one pool per configured physical DB, FarmHash32 routing, schema/primary-key checks, max-open/idle/lifetime behavior, range-locked leases/updates, transactional task creation, ordered task reads/count/deletes and Go-compatible blob encode/decode. With `use_multiple_databases=false`, logical row shards remain in the task-list key while every query uses the single configured DB; with multiple databases enabled, the FarmHash shard selects both the row shard and physical pool. It supports no-TLS PostgreSQL and the `connect_timeout`, `application_name`, and `options` connection attributes. It fails closed on TLS or unrecognized attributes instead of silently weakening connection security. This is deliberately an adapter slice, not complete PostgreSQL service parity.

The source slice does not wire server config/runtime. The existing runtime factory still only assembles SQLite/MySQL stores, and server config does not yet expose a Rust PostgreSQL store constructor. The adapter is not considered service parity until it has actual PostgreSQL validation against the Go schema and Go/Rust cross-language reads/writes, plus multi-DB routing, restart, recovery and TLS tests.
