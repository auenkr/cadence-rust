# Matching inbound metrics implementation notes

Go's inbound Matching handler uses operation scopes from `go/common/metrics/defs.go`. `MatchingAddTaskScope` is an internal task-manager scope, not an extra RPC; the RPC handler scopes are AddActivityTask and AddDecisionTask separately. Each handler starts `cadence_requests_per_tl`, stops `cadence_latency_per_tl`, records `cadence_latency_per_tl_ns`, and classifies failures in `handlerContext.handleErr`.

The Rust trait methods are the common logical request boundary: the Thrift dispatcher invokes the same `MatchingApi` methods as native gRPC. The optional sink is no-op by default. The current source wraps all 13 public methods once, with Go operation names, request/failure/latency metrics, status detail classification, and a drop guard that records latency when a long poll is cancelled. Matching task-list tags follow `GetTaskListTag`: normal names are retained, sticky and ephemeral names are masked as `__sticky__` and `__ephemeral__`, and absent/unknown names become `_unknown_`. Semaphore tags use `semaphore_name`.

Domain UUID fields use the configured Matching domain-cache resolver when a runtime domain cache is installed. This resolver reads only the current cache snapshot and never performs a synchronous persistence lookup from the RPC handler; a UUID absent from the snapshot is omitted from the telemetry tag. Standalone Matching construction falls back to the in-memory domain store. This affects telemetry dimensions only: existing request/business domain resolution still uses its current AppState path, which can lack domains present only in the durable Matching cache. Methods that accept a domain name retain it. Task-list and semaphore dimensions use Go's ASCII-compatible Tally value sanitizer. The shared recorder now accepts a request-scoped context: gRPC calls read `rpc-caller` metadata and tag transport `grpc`; the Thrift HTTP adapter reads `Rpc-Caller` and tags transport `http`, then scopes the dispatch future with Tokio task-local state. TLS HTTP reaches the same adapter and uses the `http` transport label. Native TChannel extracts reserved `cn` as caller (`as` is the argument encoding) and tags transport `tchannel`, then scopes the same Thrift dispatch. The shared trait recorder prefers scoped transport context over its internally constructed tonic request metadata. This context is task-local, so concurrent requests cannot overwrite each other's tags. An absent caller is an empty string, matching `CallerTag("")`.

Source tests exercise gRPC trait invocation with caller metadata, Thrift dispatch with caller/transport context, and TChannel `cn` extraction through the shared dispatcher; they assert one request event per call. Recorder tests cover success, generic failure, typed QueryFailed, task-list aliases, unknown dimensions, cancellation latency, and concurrent context isolation. They were not executed because the runtime lane owns Cargo/Go execution.

No service-completion or parity claim follows from these source tests. Production sink injection through runtime configuration and an executable mixed-cluster Go/Rust comparison remain outside this isolated source slice.

## AddTask traffic counter

The Rust AddDecisionTask and AddActivityTask paths now emit Go's `cadence_tasklist_request` at the engine-equivalent point: after task-list/domain validation and domain-name resolution, before task-list manager lookup. It is emitted only for normal, non-forwarded requests. The `AddTask` scope tags are `domain`, sanitized `tasklist`, `tasklistType` (`decision_task` or `activity_task`), and `matching_host`; the host value comes from the OS hostname, matching Go's default `HostName`. A no-op sink stays the default; callers with `Matching::with_metrics` receive the event. The recorder unit test checks the event/tag set and verifies sticky and forwarded exclusions. A Go handler oracle test now captures the same two exported Tally counter keys and checks forwarded exclusion; it has not been executed, and no captured Rust-vs-Go output comparison exists yet.

## Task-list manager registry gauge

`QueueRegistry` now records `tasklist_managers` as a gauge under `operation=TaskListMgr` whenever manager membership changes. Reusing an existing manager does not emit an update; removal of a stopped owner, explicit unload, ownership reassignment/eviction, and shutdown report the remaining registry size. Replacement produces the matching remove/add transition, and stale handles cannot decrement the gauge for a replacement. The sink is shared with `Matching::with_metrics`; the no-op sink remains the default, and production runtime configuration still does not install an exporter. A lifecycle source test covers create/reuse, stopped-owner replacement, stale unload, membership reassignment, and shutdown. The Go registry oracle test now snapshots `tasklist_managers+operation=TaskListMgr` through its real Tally client and checks the same-ID replacement/stale-unregister states; it and the Rust test are unexecuted, with no captured cross-language output comparison yet.

## Remaining Go Matching metric inventory

The non-test Go call sites in `go/service/matching` contain additional telemetry families beyond the inbound handler scopes. The Rust sink currently emits inbound RPC events and History-client events. Queue QPS, poller snapshots, and partition/status responses are business data and do not establish parity for these metric families.

* Engine AddTask emits `cadence_tasklist_request` under `MatchingAddTaskScope`, tagged with domain, task-list name, `task_list_type` (`decision_task` or `activity_task`), and Matching host. It is conditional on a normal, non-forwarded task list. Rust reports internal QPS but currently has no equivalent sink event.
* Task-list manager lifecycle emits `TaskListManagersGauge` under `MatchingTaskListMgrScope` (`operation=TaskListMgr`) when registry manager membership changes. Rust registry lifecycle has no matching telemetry event.
* Adaptive scaler emits `CadenceRequests`/`CadenceFailures` under `MatchingAdaptiveScalerScope` (`operation=adaptivescaler`), partition up/down/drained and isolation rebalance/group up/down counters, and scaler threshold/config gauges. Rust scaler/registry decides partition changes but does not publish this metric family.
* Task-list matcher emits per-task-list counters/timers/histograms for sync/async local and forwarded poll attempts, poll success/timeout/already-started, local/remote match direction, forwarding/query/task latency, throttling, expired/unknown tasks, lease/buffer outcomes, standby completion, isolation success/leaks, poller counts, task count/backlog/lag, rate limit, partition config and partition mismatch. The relevant Go constants are grouped under `SyncMatch*`, `AsyncMatch*`, `Forward*`, `Poll*`, `LocalTo*Match`, `RemoteTo*Match`, `StandbyClusterTasks*`, `Isolation*`, `Lease*`, `TaskCountPerTaskListGauge`, `TaskBacklogPerTaskListGauge`, `TaskLagPerTaskListGauge`, `RateLimitPerTaskListGauge`, and `TaskListPartition*`. No equivalent event recording was found in the Rust task manager/reader/writer/dispatch/scaler modules during this audit.

Useful Go anchors: `go/service/matching/handler/engine.go` (`CadenceTasklistRequests`), `go/service/matching/tasklist/task_list_registry.go` (`TaskListManagersGauge`), `go/service/matching/tasklist/adaptive_scaler.go` (`CadenceRequests`/`CadenceFailures`), and `go/service/matching/tasklist/matcher.go` plus `task_list_manager.go` for matcher and queue metrics. Port each family with its exact labels and conditions; don't infer emissions from QPS or task-list status values.

### Matcher telemetry branch audit (2026-10-20)

Go `InternalTask.IsForwarded()` is derived from the transient `forwardedFrom` value created from an AddTask request; it is not part of persisted `TaskInfo`/SQL `TaskData`. A forwarded AddTask is sync-match-only at the receiving partition: on failure that receiver returns `RemoteSyncMatchedError`, and the child partition persists the original task. Therefore a durable/backlog task must not inherit a forwarded flag from the failed request. Rust now carries the explicit forwarded bit only through `QueueHandle::try_sync_match_forwarded` / `offer_forwarded_backlog` into `SyncTask` and `DeliveryTask`; normal sync and all persisted queue claims carry false. A focused source test verifies the bit survives the rendezvous. This is the information needed for direction metrics without guessing from queue ownership or partition status.

Go `matcher.go` records `PollSuccessPerTaskListCounter` after obtaining a task (including its forwarding branches), and additionally `PollSuccessWithSyncPerTaskListCounter` for sync/query work. `PollTimeoutPerTaskListCounter` is emitted only on the blocking matcher timeout branches, not cancellation, empty queue release, History errors, or every empty poll. The engine emits decision/activity `AlreadyStarted` only for `EntityNotExistsError`, `WorkflowExecutionAlreadyCompletedError`, and `EventAlreadyStartedError` start outcomes. `emitForwardedFromStats` counts one of local-to-local, local-to-remote, remote-to-local, remote-to-remote using `InternalTask.IsForwarded()` and the incoming poll's `forwardedFrom`. Isolation match/success counters are emitted only if `partition_config` has `isolation-group`; missing `original-isolation-group` defaults to current group, and success is equality with poller isolation group. Go definitions/exported names are in `go/common/metrics/defs.go` near Matching metrics definitions (poll success around 3060; exported names around 4040–4120).

Rust has trustworthy inbound AddTask forwarding signal and now preserves it for sync handoff; it deliberately resets that signal when the child falls back to its durable queue, matching Go's transient marker. It still lacks the incoming forwarded-poll marker in `TaskDispatcher` and a task-list scoped metric sink at delivery time. Do not claim poll/direction/isolation telemetry parity until those signals and the exact matcher timeout branch are connected and covered by event-level tests. Cargo/Go validation remains deferred while the swim build lane is active.
