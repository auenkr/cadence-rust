# Matching inbound metrics implementation notes

Go's inbound Matching handler uses operation scopes from `go/common/metrics/defs.go`. `MatchingAddTaskScope` is an internal task-manager scope, not an extra RPC; the RPC handler scopes are AddActivityTask and AddDecisionTask separately. Each handler starts `cadence_requests_per_tl`, stops `cadence_latency_per_tl`, records `cadence_latency_per_tl_ns`, and classifies failures in `handlerContext.handleErr`.

The Rust trait methods are the common logical request boundary: the Thrift dispatcher invokes the same `MatchingApi` methods as native gRPC. The optional sink is no-op by default. The current source wraps all 13 public methods once, with Go operation names, request/failure/latency metrics, status detail classification, and a drop guard that records latency when a long poll is cancelled. Matching task-list tags follow `GetTaskListTag`: normal names are retained, sticky and ephemeral names are masked as `__sticky__` and `__ephemeral__`, and absent/unknown names become `_unknown_`. Semaphore tags use `semaphore_name`.

Domain UUID fields are best-effort resolved through the in-memory domain store before recording; methods that accept a domain name retain that name. Task-list and semaphore dimensions use Go's ASCII-compatible Tally value sanitizer. The Rust transport currently has no shared request context carrying YARPC caller/transport values into the trait boundary; those context tags remain to be threaded from gRPC metadata and Thrift HTTP headers. Existing source tests exercise the shared trait path through both gRPC trait invocation and Thrift dispatch and test success, failure, classification, task-list aliases, and cancellation. They were not executed because the runtime lane owns Cargo/Go execution.

No service-completion or parity claim follows from these source tests. Production sink injection through runtime configuration and an executable mixed-cluster Go/Rust comparison remain outside this isolated source slice.
