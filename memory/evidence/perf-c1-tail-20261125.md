# c1 tail: queue v2 limiter trigger audit (2026-11-25)

Branch `perf-c1-tail`, base `9ed936775`. Source audit only. No code change and no CI run.

## Question

Does Rust trigger the transfer task-load limiter more often per wall-clock
time than Go? A difference there would explain the c1 p95 gap. It was about
100 ms against 56.8 ms in one run, and a tie at 100.5 ms in another.

## Compared (Go `service/history/queuev2` against Rust `cadence-history`)

| Item | Go | Rust | Same? |
|---|---|---|---|
| Load trigger | `notify()` does a non-blocking send on a 1-slot channel (`virtual_queue.go:320`) | `notify_tx.try_send(())` on a 1-slot mpsc (`virtual_queue.rs` `notify`) | yes, coalesced |
| Run loop | `select` on ctx.Done and notifyCh, then `loadAndSubmitTasks` | same, with `tokio::select!` | yes |
| Permit order | `Wait` first, then lock, then check `sliceToRead`, pause and page size | same order | yes |
| Re-notify | if the slice has more tasks or a next slice follows | same | yes |
| Limiter creation | one `NewDynamicRateLimiter(MaxPollRPS)` in `queue_base.go:159`, shared by all virtual queues | one `new_dynamic_rate_limiter(max_poll_rps)` in `queue_base.rs:155`, shared | yes |
| Bucket | `rate.Limiter`, burst `max(ceil(rps),1)`, starts full, `Wait` reserves and sleeps the delay | `DynamicRateLimiter::reserve`, same burst and start-full, reserve then sleep | yes (20 rps, burst 20) |
| Config refresh | every 5 s (TTL) | on every call | constant in the benchmark, so no effect |

I found no Rust-only extra, earlier or un-debounced limiter permit. The
notification-coalescing and timer paths match Go. This agrees with
`perf-queuev2-loads-20261125.md`, which found equal permits per workflow.

## Conclusion

Nothing that "must match Go exactly" was found. A change to the limiter or
the load trigger would therefore be a deviation from Go, and the strict
parity rule forbids it. The c1 tail is not caused by extra permits. It
most likely comes from the burstier arrival timing of Rust's own task
completions, which the evidence already shows.

I did not run `cadence-history` CI, `history-mixed-gate` or the 5-rep
benchmark, because nothing changed in the code. Master's results stay the
reference. No wf/s, percentile or History MiB tables were produced.
