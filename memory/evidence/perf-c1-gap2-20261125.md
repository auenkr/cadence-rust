# History decision latency follow-up (2026-11-25)

The benchmark branch started at master `76bbc723d`, which already contains
`8ea8106ca`, the History fix that advances the immediate max read level before
notifying the transfer queue. Go holds the shard write lock across both
operations. Before the Rust fix, the awakened reader could observe the old
level and defer the task until another poll.

The pre-fix [trace run](https://github.com/auenkr/cadence-rust/actions/runs/45514180239)
measured 215 of 1,010 notify-to-executor gaps over 30 ms (p95 39.97 ms).
AddDecisionTask send to RecordDecisionTaskStarted ingress was 1.01 ms at p95
and handler ingress to response conversion was 4.26 ms at p95. The original
40 ms mode was visible before Matching or the RecordDecisionTaskStarted handler.

The previous [post-fix run](https://github.com/auenkr/cadence-rust/actions/runs/45519128738)
at `8ea8106ca` ran five paired batches of 1,000 measured workflows at c1.
Counts below come directly from `successful_latency_samples_ms` with a strict
`> 60` ms cutoff. Its runner was Ubuntu 26.04.1, AMD EPYC 9V74, 4 logical CPUs
and 15 GiB RAM. Each service was limited to 1 CPU and 1,400 MiB, and MySQL was
limited to 1.5 CPUs and 1,800 MiB.

| Arm | >60 ms per repetition | Pooled >60 ms | Median workflows/s |
|---|---|---:|---:|
| Go | 249, 332, 280, 155, 252 | 1,268 / 5,000 (25.36%) | 17.07 |
| Rust History | 190, 227, 184, 186, 218 | 1,005 / 5,000 (20.10%) | 21.38 |

## Queue v2 limiter result

The final traced run measured 3,000 successful workflows per arm, plus
warmup, on AMD EPYC 7763 with 4 logical CPUs, 15 GiB RAM, Ubuntu 26.04.1
and image `ubuntu26 20261116.202.1`. Container limits matched the earlier
benchmarks. The artifact verifier passed. Standalone History SHA256
`e4a4f489dbc448686f54a9af29cb11e84d64afd3cdb05e0b934336032836284f`.

| Arm | >60 ms per repetition | Pooled >60 ms | Median workflows/s |
|---|---|---:|---:|
| Go | 24, 18, 19 | 61/3,000 (2.0%) | 22.95 |
| Rust History | 162, 162, 182 | 506/3,000 (16.9%) | 25.30 |

| Stage interval | Samples | p50 ms | p95 ms | >30 ms |
|---|---:|---:|---:|---:|
| Notify logged to v2 task read (second decision) | 3,030 | 0.053 | 37.066 | 506 |
| v2 task read to executor pickup | 6,060 | 0.120 | 0.265 | 0 |
| AddDecisionTask send to RecordDecisionTaskStarted ingress | 6,060 | 0.947 | 1.255 | 1 |
| RecordDecisionTaskStarted ingress to gRPC response conversion | 6,060 | 2.691 | 3.647 | 0 |

Every one of the 506 second-decision notify-to-read gaps above 30 ms
had a task-load limiter wait above 5 ms. Their median notify-to-read gap
was 36.629 ms and their median limiter wait was 49.529 ms. The limiter
can start waiting before the decision notification, so these intervals
overlap and should not be subtracted as successive stages. For measured
workflows above 60 ms, 888/1,012 decision tasks had a limiter wait above
30 ms, versus 4/4,988 for measured workflows within 60 ms.

To reproduce the counts, download the `frontend-matching-paired-benchmark`
artifact from the trace run. Pair `c0_transfer_task_read` with
`c1_queue_rate_limiter_wait` on workflow ID, run ID and task ID in each
`services-*-rust.log`. Join measured workflow latency by workflow and run
ID from the corresponding `result-*-rust-c1-samples.json`. Count waits
above 30 ms using the `wait_ms` field. For notify-to-read, pair the
single `b_transfer_notified` with the later of two transfer reads for
the same workflow and run. The 3,030 trace pairs include warmup.

The transfer queue v2 task-load limiter accounts for the repeated wait
in the traced Rust History arm. Go and Rust both default
`history.transferProcessorMaxPollRPS` to 20, and both reserve a permit
before reading the virtual queue. Higher Rust throughput can increase
poll demand, but this experiment did not directly compare Go's permit
consumption with Rust's. An implementation difference that would justify a
parity-preserving fix was not established. The default limiter and
transport settings were retained. The c1 above-60-ms target remains unmet.
