# Review: dual-node Matching Prometheus fixture (2026-10-27)

Reviewed `d0b68d53e8193dcce9cb3fb5bde8541db1a08324` for secondary config generation, process lifecycle, concurrent scrape capture, validator consumption, and endpoint provenance.

## Finding and recommendation

The secondary config is generated by replacing the primary `listenAddress` with a separately allocated loopback port. `startSecondaryRust()` reads `CADENCE_RUST_MATCHING_SECONDARY_CONFIG`, and all secondary restarts use that same function; primary restarts continue using the primary config. Scrape capture is single-threaded and visits both addresses, retaining each address in the compressed record.

There was one gate hole: scrape failures are intentionally swallowed, and the validator discarded each record's `endpoint` field and merged all bodies. Thus the new fixture could pass with every required sample present on the primary while the secondary endpoint never returned samples. It also failed to include the secondary config in durable config hashes/redacted config evidence. The validator now requires a nonempty scrape from every configured endpoint and reports the captured endpoint set; durable evidence includes the secondary config and its hash. The existing positive SDK query sample assertion remains intact.

Integration recommendation: the fixture is appropriate for a mixed gate once this endpoint-presence assertion passes. The review does not establish runtime correctness; only syntax and diff checks were run. Parent owns the live gate.
