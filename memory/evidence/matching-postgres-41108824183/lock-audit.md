## Evidence and limits

The run log records `ListTaskListPartitions` entering the handler, completing admission, domain resolution, partition counts, and owner lookups, then completing the engine call. The supplied successful native probe completes in 776 us. Roughly 25 seconds later the readiness RPC stalls. `probe.log` reports the Go Frontend deadline and a direct gRPC `Waiting for LB pick` deadline. The process sample has 10 sleeping threads at `futex_do_wait`, zero CPU ticks over 500 ms, and listener `Recv-Q 2`; the server log has no HTTP/2 SETTINGS or shutdown markers. These establish a stall and its timing, but do not identify a held mutex or its owner.

## Lock and callback paths checked

* `launcher.rs:44-109`: `dynamic_bool_property` and `dynamic_i64_property` acquire the admin overlay mutex, derive `PropertyValues`, and call `evaluate` before the guard leaves scope. `matching_runtime.rs:1215-1225` similarly keeps the overlay guard while resolving the shutdown duration. With a runtime provider, `PropertyValues::evaluate` reaches `OpenFeatureRuntimeProvider::evaluate` -> `OpenFeatureClient` -> `client::evaluate`.
* `client.rs:130-133,147-162`: evaluation briefly acquires global `REGISTRATION` to clone the provider; the guard is dropped before `provider.resolve`. Thus the normal read chain is admin overlay -> short global registration lock -> provider resolve. The configured Unleash provider `resolve` reads its own feature snapshot under its repository `RwLock`; it has no callback or reference to the admin overlay. No reverse edge from that provider path back to the overlay was found, so the held overlay guard alone does not prove a cycle.
* `client.rs:74-117`: provider registration holds `REGISTRATION` across constructor and `init`. Matching's provider constructor/init is selected in `launcher.rs:661-669`; Unleash init only marks its provider ready. This startup path is synchronous, but does not form a cycle with the later overlay readers based on the configured provider implementation.
* `client.rs:120-130`: final deregistration holds `REGISTRATION` while calling provider `shutdown`. Unleash shutdown marks itself not-ready and joins its poller and reporter (`unleash.rs:520-534, 561-569`). Those workers do not acquire `REGISTRATION` or the admin overlay in the inspected source. This is a lock held over joins and merits future caution, but no cycle to the stalled request is established by source here.
* `matching_runtime.rs:920-1005` and `matching_domain_cache.rs:793-814`: domain-cache registration takes `refresh_lock`, installs callbacks under the callbacks mutex, snapshots cache state, then invokes catch-up. The changed callback takes the failover-version mutex, syncs domain metadata, and conditionally clones the native registry under its mutex before spawning async poll-release work. No callback path from these locks into OpenFeature/admin dynamic config was found. Shutdown unregisters the callback without holding the overlay mutex.
* `AdminState::custom_search_attributes` is separately locked for `AddSearchAttribute` (`admin.rs:403-426`); this handler does not acquire dynamic config or invoke an OpenFeature callback. `matching_config.rs` contains pure property-key/default readers and no mutex acquisition.
* Dynamic-config file/store refresh tasks replace the overlay under its mutex (`matching_runtime.rs:748-800`). They perform file or config-store refresh before acquiring the overlay lock and do not invoke property callbacks while holding it.

## Conclusion

No concrete reachable self-lock or lock-order cycle capable of explaining the stalled request is proved by this source audit. No runtime correction or regression test is justified from the available evidence. In particular, an all-sleeping process and a queued gRPC listener are consistent with a lock wait but do not show which thread owns a lock or that a cycle exists.

Unresolved paths require runtime owner evidence (for example, thread stacks or lock-wait instrumentation from a reproducible occurrence): the exact reason all Tokio workers stopped accepting/processing after the successful probe; whether the `Waiting for LB pick` result reflects a stalled accepted HTTP/2 connection or upstream listener backlog; and the owner/contended object behind the futex waits. Startup, watcher, and callback lock-order assumptions above are source-bounded and do not exclude unrelated synchronization, driver, or runtime stalls.
