## Predeclared criteria (fixed before dispatch)
- Settings: c1, mysql, default dynamic config, `control_ref=origin/master`, `rust_services=frontend,matching,history`, `sdk_openloop=false`, `repetitions=5`,
  shape echo, 1000 requests/rep, warmup 10, `source_ref` = master head `88da8c3a9b6043a7b7b273f5e94cd0b1567dde44`.
- Rates (`target_rate`): 10, 15, 18, 20, 22 wf/s, and unpaced (empty). 4 independent runs per rate (24 runs), all dispatched in parallel. Three arms per run (go, control, rust).
- Statistic: all successful request latencies of an arm pooled over the 4 runs x 5 reps; p90 and p95 of that pool. Difference = (Rust - Go) / Go.
- Interval: run-cluster bootstrap (resample the 4 runs with replacement, then reps within each selected run, seed 1, 20 000 draws), 95% percentile CI of (Rust - Go) / Go.
- **PASS for a rate** iff the CI upper bound is <= +5% of Go for BOTH p90 and p95. Otherwise FAIL (reported as such, no re-runs to rescue a failure).
- Rate-matching sanity: per-arm median achieved wf/s within 3% of target (not applicable to unpaced); reported, not part of PASS.
- Order balancing: `paired-run.py` three-arm mode already rotates arm order per repetition (go/control/rust, control/rust/go, rust/go/control, ...), so no fixed order
  exists. With 5 reps the rotation is not perfectly balanced (positions 2/1/2 for go, 1/2/2 for rust), identical in every run; this residual is documented, not changed.
- Informational (not part of verdict): p50, p99, share >= 75 ms, CPU per run, binary SHA256s, Rust vs control (A/A) difference.

## Why unpaced fails on p90 (permit-timing evidence)
perf-c1-permit-timing-20261125.md showed the transfer-queue limiter (20 rps / burst 20 per shard) is a pure function of the request series: waits appear when a shard receives a cluster of workflows
(3 permits each) faster than the bucket refills. Unpaced, Rust's closed loop is faster (25.1 vs 22.5 wf/s, p50 27 vs 42 ms) so each shard sees permits faster; p90 94 / p95 100 / p99 110 ms is the
limiter plateau (waiting for refill), share >=75 ms 15.7% vs 4.0%. Rust and its A/A control are identical (p90 94.0 vs 93.7), so the effect is not a Rust-specific defect or noise but the same
limiter reacting to higher throughput. With a paced open-loop start rate (10-22) the offered load is identical and Rust is at or below Go at p50 and only noise-limited at p90/p95.
The raw request-rate in unpaced Rust (25 wf/s over 4 shards, ~19 permits/s/shard) is at the limiter's 20 rps edge; Go at 22.5 wf/s stays just under.

## Parity-safe Rust change candidates (NOT implemented)
I found none that reduces permit clustering without changing timing semantics:
- `rust/crates/cadence-history/src/queuev2/virtual_queue.rs:324` (`task_load_rate_limiter.wait` before the lock and `GetTasks`) and `queue_base.rs:288` (`wait_for_task_writes`, shard write-lock acquire/drop,
  `deps.rs:548`, `wiring/assembly/shard_adapters.rs:419`) are line-for-line equivalents of Go (`virtual_queue.go:327-441`, `getImmediateTaskMaxReadLevel` RLock). Moving the limiter wait after the
  read-level gate or spacing loads would change when permits are taken, which is a behaviour change, not parity.
- Any reduction in clustering requires adding delay or batching beyond Go's semantics (also concluded in perf-c1-permit-timing-20261125.md). Not recommended.
