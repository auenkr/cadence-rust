The 40ms sits in DecisionTaskScheduled->Started (History transfer -> Matching AddDecisionTask -> poller -> RecordDecisionTaskStarted), Rust ~3-4x more often than Go in run 1.

## Step 2: Rust trace
- Transfer queue notify/poll (`transfer_queue_processor_base.rs`): `notify_new_task` wakes the pump immediately; same as Go. No deviation.
- Deviation found: `launcher.rs matching_resolver` called `endpoint_channel` (new `connect_lazy` channel) on every
  AddDecisionTask/AddActivityTask, so each call opened a fresh TCP + HTTP/2 connection (handshake + SETTINGS exchange,
  delayed-ACK exposure) and dropped it. Go (yarpc) keeps a pooled connection per peer.
- Fix: cache one lazy `Channel` per Matching gRPC address in the resolver (cloned per call, reconnects on failure).

## Conclusion (time-boxed, done condition NOT met)
- 40ms always sits in DecisionTaskScheduled->Started for dec1 AND dec2 of the same workflow (activity gap ~0). In the `rust_services=history`
  arm Go Matching does the dispatch, so the unexplained delay is in Rust History between persisting the Scheduled event and
  Go Matching's RecordDecisionTaskStarted landing on Rust History (transfer pickup, AddDecisionTask to Go Matching, or Go Matching -> Rust History
  RecordDecisionTaskStarted response path).
- Ruled out (no effect measured): tchannel frame coalescing (perf-history-ack), per-call channel creation (fixed here, harmless/parity improvement),
  transfer queue poll limiter, notify/poll intervals (code parity with Go).
- Next step needs instrumentation (not guessable statically): timestamp log in Rust History at (a) transfer task read, (b) AddDecisionTask send/return,
  (c) RecordDecisionTaskStarted receive/respond, to locate the 40ms. Also check the gRPC server-side (tonic/hyper HTTP2 settings: e.g. Go client
  window/ping, `http2_adaptive_window`, response flush) for RecordDecisionTaskStarted.
