# Matching query dispatch, partition refresh and failover callback audit (2026-10-30)

Scope: source comparison prompted by the ignored cases in `matching_engine_go_tests_b.rs` and `matching_engine_go_tests_c.rs`. This is a source audit, not fresh CI evidence. No Cargo, Go, formatter, runtime or mixed-cluster command was run.

## Query dispatch failure

Go source: `go/service/matching/handler/engine.go:1014-1061` allocates a buffered result channel, inserts it in `lockableQueryTaskMap`, and defers deletion for every return. `DispatchQueryTask` errors are returned directly; a non-nil response means forwarding completed; nil response means local dispatch and then `waitForQueryResult`. The ignored Go test at `go/service/matching/handler/engine_test.go:677-690` injects `errors.New("some error")` by mocking the entire `TaskListManager` method. It does not exercise a failure produced by Go's concrete matcher.

Concrete Go `tasklist/matcher.go:278-310` can fail `OfferQuery` when its context is canceled, or when forwarding a query returns a non-`ErrForwarderSlowDown` error. A slow-down releases the forwarding token and continues waiting for a local poller; caller cancellation returns `ctx.Err()`. The matching engine's deferred query-map deletion covers each path.

Rust's ignored case is likewise explicitly a missing mock seam, not an observed behavior defect. The public durable query implementation (`grpc_matching.rs`, `QueryWorkflow`) gets the queue, registers the task ID with a guard, and either locally offers, forwards, or returns the forwarding/deadline status. The registration guard removes the waiter, query-index entry, and pending offer on return, timeout or dropped RPC; the typed `NativeMatchingEngine` has the same guarded-registration rule in `matching_engine_query_native.rs`. `NativeQueryError` retains worker query error bytes and status errors separately. Concrete Rust failure paths therefore have cleanup and propagation; the test cannot recreate the Go mock's arbitrary pre-dispatch error without adding a fault-injection seam. No production patch is justified by this comparison. If a deterministic proof is required, use a narrowly scoped internal dispatch trait/seam and assert returned error plus absent query-index entry and pending offer; do not turn a non-sticky no-poller deadline into an immediate error, which would change Go behavior.

## Public partition refresh failure

Go `tasklist/task_list_manager.go:425-445` waits for startup; when the pushed config is nil it reloads the root config and returns the persistence error unchanged; with a non-nil pushed config it only advances the in-memory version and returns nil. A persistence failure therefore occurs on the nil/reload branch, not in the ordinary pushed-config branch. Notification failures from `notifyPartitionConfig` are logged and aggregated there; its caller logs the aggregate and does not return the notification error.

Rust's public RefreshTaskListPartitionConfig handler validates and routes the RPC to the durable queue registry and propagates queue/persistence errors with `?` through the tonic result. Existing `matching_partition_cancellation_tests.rs::refresh_rpc_persistence_failure_matches_go_and_observes_expired_caller` covers permanent, timeout and throttled persistence errors, including caller cancellation/retry behavior. The ignored test `refresh_task_list_partition_config_manager_error_is_propagated` seeks to inject an error into a mocked manager method that does not exist in Rust's public registry implementation. That is test-only missing evidence, not proof of a public propagation gap. One remaining distinct parity check, if required, is whether Rust refresh of an absent partition with nil config reproduces Go's root metadata reload and exact persistence error mapping; it is not what the ignored injected-manager case currently tests.

## Failover callback integration

Go `handler/engine.go:1707+` advances its notification-version baseline, filters through `isDomainEligibleToDisconnectPollers`, enumerates normal decision/activity and sticky decision task lists, then releases eligible pollers. The old ignored Rust test only objected that the production closure was private. Current Rust source has registered-callback integration tests in `matching_failover_callback_tests.rs`: they start the actual domain cache, check catch-up establishes a baseline without releasing a blocked poll, exercise local/active-active/stale exclusions, then verify an eligible update releases the poll while retaining the same owner. A second test attaches the native registry after catch-up and verifies the registered closure reads the shared slot. This closes the former helper-only integration evidence gap at source/test level; exact-candidate CI and cross-service failover execution remain external acceptance evidence, not claimed here.
