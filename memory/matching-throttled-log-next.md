# Matching long poll validation and throttled logging

On branch `t3/matching-runtime-owner` at the task start (`c253324be`), Matching's Rust gRPC decision and activity poll handlers had no equivalent of Go `common.ValidateLongPollContextTimeoutIsSet`. Go returns `common.ErrContextTimeoutNotSet`, a `types.BadRequestError` with message `Context timeout is not set.`, and logs `Context timeout not set for long poll API.` through the handler's shared throttled logger. Go configures that logger with `matching.throttledLogRPS` (default 20).

Rust now checks the incoming `grpc-timeout` metadata through `matching_sync::request_deadline` in both poll handlers before consuming the tonic request. Missing/unparseable timeout metadata returns gRPC `InvalidArgument` with the Go message. A single logger instance is initialized from the Matching dynamic config overlay and shared by both methods. It has an injectable clock and sink; production output uses `eprintln!`.

Also corrected `matching_quota::DynamicBucket::refresh`: Go's `rate.Limiter.SetLimitAndBurst` updates against its last recorded time and does not first advance to the configuration refresh time. The extra `tokens(now)` call was removed. Added unrun regressions for both missing-deadline RPCs, shared poll log throttling, and a depleted bucket whose rate changes at refresh.

Follow-up parity review verified that Go performs worker quota admission before deadline validation, so Rust now preserves quota error precedence. The TChannel bridge is already present: `tchannel.rs` computes the call TTL deadline, `thrift_matching.rs::rpc_request` calls tonic 0.12.3 `Request::set_timeout`, and tonic 0.12.3 writes `grpc-timeout` metadata; `matching_sync::request_deadline` reads it. Tonic's `GrpcTimeout` middleware reads the header without removing it. No duplicate TChannel poll handler is needed.

The logger now wraps `cadence_common::rate_limiter::RateLimiter` with Go `quotas.NewDynamicRateLimiter` behavior: sample at construction, share the token bucket, refresh after the five-second TTL using the `TTL - 1ns` comparison, and call `set_limit_and_burst` without advancing its clock. At `t=5s`, the logger refreshes the rate but emits no log: its latest limiter call was at `t=4.999999999s`, so the new 1 RPS setting has accrued only 1ns. The regression asserts the refreshed rate/burst and `last_update` at 5s, then checks no permit at 5.999999998s and a permit at 5.999999999s. Regression source covers initial default 20 token capacity, zero rate, and post-TTL rate sampling. Tests remain unrun; no Cargo/build/test/service commands were run.

Review retraction: an independent review inferred that the permit should exist at exactly 5s. That inference conflated config refresh with token refill; the refresh uses the limiter's latest recorded time, as confirmed in Rust `RateLimiter::set_limit_and_burst` and Go `rate.Limiter.SetLimitAt` behavior. The zero-emission assertion at 5s is retained; direct assertions now separately establish that the config refresh did occur at that boundary.
