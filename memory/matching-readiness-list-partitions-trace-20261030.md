## Native handler path

`grpc_matching.rs::list_task_list_partitions` enters the metrics wrapper, checks host quota (with neither domain UUID nor domain name supplied, so quota does not resolve the domain), clones the request, then calls `domain_id_by_name`. With the production `MatchingDomainCache`, this runs on `spawn_blocking`: a cache hit returns immediately; a miss does a persistence existence lookup and then a serialized refresh scan before returning the UUID. A successful read-through inserts metadata into the local domain view. Only after that does it parse `TaskListName`, read activity then decision partition counts through the dynamic-config provider, and resolve each partition's owner. The config provider locks the config overlay and reads task-list scoped values. A shard-router owner resolution is awaited; membership-only owner lookup is synchronous. Owner errors are deliberately discarded and produce an empty owner field. There is no PostgreSQL query in the partition-count or owner-result construction itself.

There is no demonstrated recursive lock in this sequence. The domain-cache miss path releases its cache read lock before persistence access, takes the refresh lock, and rechecks the cache; metadata publication into `InMemoryDomainStore` takes that store's write lock after persistence returns. The handler does not propagate the gRPC deadline into `domain_id_by_name` or the cache's persistence calls. Cache operations use their own three-second persistence timeout(s), while a cold lookup may perform the existence check plus refresh. This makes a cold name lookup a plausible dependency stage to measure, but source review alone does not prove it is the timeout cause.
