Go references: `service/matching/tasklist/matcher.go` `OfferQuery`, `Poll` and `fwdrAddReqTokenC`, plus `forwarder.go` `ForwardQueryTask` and token generations. Go first attempts a nonblocking unbuffered local send, then selects local send, add-request token, or context cancellation. A forwarded ServiceBusy/slowdown disables forwarding for the remainder of that local attempt. Query forwarding does not use the add-task rate limiter.

Changed the native offer into a cancellable rendezvous: `next()` takes an offer under the same mutex used to withdraw it and decide a forwarding race. Acceptance wakes the offer; completion is registered before the offer, so a fast worker response is retained. Cancellation removes a pending offer, and a dropped poll does not reserve it. Registration/index generations protect replacement, including concurrent publication and channels without an index. IDs remain raw `GoString` bytes. Remaining parity gap: Go's initial nonblocking send guarantees a poll already waiting in the Go select is preferred over an immediately available forward token. A Rust `next()` future parked inside the outer poll `select!` cannot be committed by the offer without also atomically choosing that outer select branch; the current implementation queues the offer and races the permit, so a ready permit can win before the parked poll is rescheduled. A correct solution needs a shared cancellation-safe selection/commit protocol spanning native decision polling and query offering (including other poll branches); scheduling yields or buffered reservations do not establish Go semantics. Simultaneously ready choices in the subsequent Go select are also randomized, whereas this implementation prioritizes an already accepted handoff. Thus this is an incomplete parity fix, not a service-completion claim. Poll error completion by task ID also needs review for ID reuse across generations; Go normally generates UUID IDs.
