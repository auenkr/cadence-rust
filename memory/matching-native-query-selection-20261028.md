# Native query selection follow-up, 2026-10-28

Scope: `rust/crates/cadence-matching/src/matching_query_native.rs`; `matching_engine_query_native.rs` and `matching_engine_poll_native.rs` were inspected and left unchanged. Parent owns registration and integration. No Cargo/Go/rustfmt/build/test/check commands, CI dispatch, staging, commit or push were run.

Implementation: `QueryChannel::offer_or_forward` now retains an already-ready forwarding result while one or more decision polls have registered in `QueryChannel::next`. It checks the poller count under the same pending mutex used for offer removal. A waiting local poll can take the offer and signal the accepted oneshot; otherwise cancellation/withdrawal decrements the poller count and notifies the offer race, which can then remove the still-pending offer and forward it. The `Notified` future is enabled before checking the count to avoid losing the final poller's withdrawal notification. The decision poll uses a biased `tokio::select!` with query next first, so a local offer accepted by that registered branch is selected ahead of simultaneously ready backlog/forward work. No scheduler yield or sleep defines selection.

Tests added in the owned query module: deterministic manual-future-poll checks for a ready local poll versus ready forward token and for cancellation of the registered poll releasing that token. Raw ff/fe task IDs are asserted. Existing suite in this module covers guarded registration/cancellation, raw distinct ff/fe IDs, response/task-token construction, completion outcomes and version behavior. `git diff --check` passed for all owned source paths.

Remaining gap: the protocol does not add a delivery lease spanning the body of the decision poll's query branch. Once `next()` returns the query, cancellation of the poll while `query_mutable_state_with_deadline` is in progress can drop the query after the offer has been declared matched. Thus cancellation *after* branch commitment is not recovered/requeued by this change. The Go path's post-receive cancellation behavior needs source-level confirmation, and if the intended guarantee requires requeue, this needs a lease protocol spanning `matching_engine_poll_native.rs` query-state resolution. We also did not add new integration tests for competing persistence backlog/query delivery or query completion under poll cancellation. No runtime or compile validation was performed; all are unverified pending parent CI.
