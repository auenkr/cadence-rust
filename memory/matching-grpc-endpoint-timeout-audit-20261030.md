# Matching direct gRPC readiness timeout audit (2026-10-30)

Source and retained-artifact review only. No Cargo, Go, runtime, formatter, CI, or PR actions were run.

## Findings

- In `tests/matching-service-compat.cjs`, production `waitForRustReady` first calls Go Frontend `WorkflowAPI/DescribeTaskList`, then probes the primary Rust endpoint directly with `directPartitionOwner`. The direct RPC is `uber.cadence.matching.v1.MatchingAPI/ListTaskListPartitions`, sent to `127.0.0.1:${CADENCE_RUST_MATCHING_PRODUCTION_GRPC_PORT}`. It is not `grpc.health.v1.Health/Check` and does not call MetaAPI health. The client uses TLS only when `CADENCE_MATCHING_GRPC_CA_FILE` is set; otherwise it uses insecure credentials. `grpc-js` uses HTTP/2 for this gRPC call.
- Retained gate 41034380907 configured Matching gRPC as `127.0.0.1:10731`, advertised that port in the production command, and reported `Deadline exceeded after 10.007s, ... remote_addr=127.0.0.1:10731`. The Rust log printed the same listener address before Ringpop startup. This rules out a configured-port mismatch in that run. The timeout does not prove the RPC handler entered, nor whether it stalled in domain lookup or partition metadata work.
- Launcher source derives Matching's bind IP from `services.matching.rpc.bindOnLocalHost`, binds the TCP listener before Ringpop advertises its port, and uses the bound socket's `local_addr()` for both the advertised `grpc` metadata and serving. After membership startup, it calls `matching_service.mark_started()`, then puts the Matching gRPC future into the Tokio `JoinSet`. The main `select!` awaits `serving.join_next()` or shutdown; there is no source path where the spawned listener task is intentionally left unpolled. Normal shutdown aborts the serving tasks after withdrawal and runtime drain.
- `grpc_matching.rs` registers reflection, `MetaAPI`, and `MatchingAPI` on the same tonic HTTP/2 server. `MetaAPI.Health` waits for `Matching::wait_started`; `ListTaskListPartitions` does not use that health method and performs quota checking, domain-name resolution, and partition metadata lookups. The native integration test `matching_grpc_listener_registers_meta_health_and_gates_startup` verifies the MetaAPI health gate on a pre-bound listener, but is not evidence that the production PostgreSQL-backed handler completes.
- The captured server log ends at “Matching startup: opening admission” followed by Ringpop PINGs. The log has no per-RPC entry/exit evidence, so the timeout cannot be attributed to transport acceptance, handler dispatch, domain resolution, or PostgreSQL-backed partition metadata.

## Conclusion and discriminating evidence

No concrete port, address, TLS-mode, HTTP/2, registration, or JoinSet polling mismatch is established by source. Do not change startup/transport code based on this evidence. To distinguish causes in a follow-up gate, retain a server-side entry/exit timestamp for `ListTaskListPartitions` plus stage timings around domain lookup and partition metadata reads, alongside the existing gRPC status and endpoint. Handler entry with no exit points to handler/dependency work; no entry despite an HTTP/2 request points earlier in transport/dispatch. Keep the active 41039044942 gate owned by its parent; this audit did not poll or dispatch it.
