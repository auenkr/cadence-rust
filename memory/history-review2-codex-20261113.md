## 1. P1 — A shard that closes during initialization remains cached forever

- Rust: `rust/crates/cadence-history/src/wiring/assembly/controller.rs:81` (introduced by history-casflake); callback dispatch at lines 198–206 and publication at line 171.
- Go: `go/service/history/shard/controller.go:375` (`removeHistoryShardItem` compares the already-registered item identity), `:272` (always stops the closing item), `:497` (creation/start serialized with stop through the item's lock).
- The new guard treats every uninitialized `OnceCell` as a successor and returns false. However, the cell for this very acquisition is also uninitialized until `create_entry` returns. The shard weak reference is installed before building/starting the engine; queue processors start before the awaited DLQ startup completes. A close callback in that interval sees `Some(closing)` and an empty cell, discards the close, and never stops the engine. `get_or_try_init` subsequently publishes that same closed shard. `entry_for_shard` has no closed-state check to invalidate it, and `close_shard` fires its callback only once.
- Concrete failure: during initial engine startup, a queue processor encounters ownership loss while updating shard state or renewing the range, and its asynchronous close callback runs before cell publication. Once creation finishes, all requests to that shard reuse the closed context and fail instead of reacquiring a healthy engine. This persists while membership still assigns the shard to this host, until an independent registry removal/restart. Go removes the registered closing item even during startup, then waits on the item lock to stop its engine. The Rust identity check needs to distinguish the initializing owning cell from a successor, rather than ignoring all empty cells.

## 2. P1 — The new NDC StartTransaction call cannot perform decision failover

- Rust: `rust/crates/cadence-history/src/wiring/assembly/ndc_workflow.rs:586` and `:597` (history-xrfix's load-with-task-version implementation).
- Go: `go/service/history/execution/context.go:384` (constructs mutable state with shard/domain dependencies), `:400` (StartTransaction), `go/service/history/execution/mutable_state_builder.go:1418` and `:1936` (active version update and decision failover).
- `state_from_snapshot` constructs `OwnedNdcMutableState` with `TaskGenEnv::default()` and never installs `set_failover_context`. Thus the resulting typed state's `failover` is `None`. `TypedMutableState::start_transaction_handle_decision_failover` immediately returns `Ok(false)` in that case (`execution/mutable_state_failover.rs:50`). Fetching the active failover version in the new code does not supply the missing cluster metadata or replication policy. The installation in `EngineNdcContextHooks::build_state` does not help: this checkout uses `context.clean_snapshot()` and the standalone `state_from_snapshot`, bypassing that hook. The `None` task-version path also returns before running StartTransaction, unlike Go LoadWorkflowExecution's EMPTY_VERSION path.
- Concrete failure: load an existing global workflow with a decision started at version V1 after the workflow/domain fails over to V2, in a case where Go must fail the old decision and flush buffered events before processing the incoming non-start batch. Rust raises current version to V2 but silently leaves the V1 decision and buffer intact, omitting FAILOVER_CLOSE_DECISION and its replacement decision. Subsequent replication/conflict processing operates on state Go would have flushed, breaking the single-version decision/buffer invariant. This is an incomplete replacement of the former explicit unsupported-task-version error, not successful failover support.

## 3. P1 — Replication-task generation still misses active writes through typed NDC state

- Rust: `rust/crates/cadence-history/src/wiring/assembly/engine_close.rs:321` (history-replgen's new generation call; missed alternate caller).
- Supporting missed path: `wiring/assembly/ndc_workflow.rs:383` (suppression), `:407` (active update); `wiring/assembly/ndc_state.rs:344` (typed close); `execution/mutable_state_builder.rs:654` (only encodes generated transfer/timer tasks) and `:670` (close mutation).
- Go: `go/service/history/execution/workflow.go:207` (local-active conflicting run is terminated with active transaction policy), `go/service/history/execution/mutable_state_builder.go:1749` (history replication tasks generated for each active history batch), `:1774` (eventsToReplicationTask).
- The added generator is private to `EngineMutableState::close_transaction`. NDC writes own a different `TypedMutableState` and persist through `EngineNdcWriter`/`WorkflowContext`, so they never call it. Typed close copies already-existing task rows and encodes transfer/timer tasks; it does not create history replication rows for newly generated active events. Task-ID allocation in the context hook only processes rows already present and does not fill this gap.
- Concrete failure: in a multi-cluster global domain with replication enabled, NDC resolves concurrent runs and suppresses an older run last written by this cluster. Suppression generates a local termination (and may first fail a decision/flush buffered events), then persists it with `TransactionPolicy::Active`. The history and mutable state commit without any category-3 HistoryReplicationTask. Remote clusters never receive those newly generated close/decision/buffer events through normal replication. This is a missed caller of the replication-generation fix, independently of finding 2: the suppression path can generate active events without StartTransaction failover.

## 4. P2 — Shard range-renewal failures still bypass owner enrichment

- Rust: `rust/crates/cadence-history/src/wiring/assembly/engine_cache.rs:164` (history-lastp2's ownership-error adaptation); enrichment only accepts `Some(shard_id)` in `wiring/assembly/controller.rs:65`.
- Go: `go/service/history/handler/handler.go:2138` (looks up the owner using persistence error ShardID and constructs the redirect error).
- `SqlShardPersistence::update_shard` still converts the persistence ownership error to `ShardContextError::ShardOwnershipLost(String)` (`wiring/persistence/shard_events.rs:376`). The revised `shard_err` explicitly sets `shard_id: None`, so the new handler converter leaves it untouched and both wire transports emit an empty owner. The shard ID is known by the allocator/context at this call site, but is discarded. The new `Some(shard_id)` mapping for execution-store failures does not cover shard-store failures.
- Concrete failure: a request allocates task IDs just as its range is exhausted, another History host has stolen the shard, and renewal fails its range CAS. Even with a successful membership lookup pointing to the new host, Rust returns ShardOwnershipLost with an empty Owner. Go returns the owner address, allowing the caller to redirect its retry directly. This leaves the claimed owner-field fix incomplete on an ordinary ownership-loss path.
