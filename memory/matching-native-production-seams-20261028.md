## Behavior/data-path distinctions and known bounds

- Live task path in native registry is not diagnostic-only: `NativeQueueRegistry::get`, owner construction, and `NativeQueueHandle::{enqueue,append,append_in_domain,...}` build and drive `DurableTaskQueueBytes`, `NativeTaskWriter`, `NativeTaskReader`, and `NativeTaskDispatcher` (`matching_registry_native.rs:491-545,1027-1210,1241-1550`). But launcher does not instantiate it.
- `NativeQueueRegistry::with_scaler_starter` is an injection seam; owner starts it only for eligible root normal owners (`matching_registry_native.rs:1196-1209`). No production scaler callback is attached. Legacy `Matching` dynamic scaler/partition paths in `grpc_matching.rs` do not prove native scaler production support.
- Membership callbacks and `unload_non_owned` are actual queue ownership operations (`matching_registry_native.rs:918-1024`), while shard-distributor diagnostics/trace helpers do not attach those callbacks. Launcher currently attaches legacy membership only.
- `matching_native_status::RawStatusService` only handles unary tonic errors returned as HTTP headers; file docs explicitly say streaming trailers are unsupported. It rewrites `grpc-message` only when error has private raw marker; ordinary statuses are unchanged. Invalid `GoString` detailed errors intentionally omit grpc-status-details-bin (`matching_native_status.rs:33-39,66-82`). Registration must wrap the service that emits `raw_status`/`raw_detailed_status`; wrapper alone cannot make standard String-backed statuses byte-preserving.
- Native Thrift conversion currently has explicit unsupported outcomes: `thrift_matching_native_extra.rs:188` says only activity-scheduled history events are decoded; inspect/port remaining event variants before claiming full Thrift parity. `thrift_matching_native.rs`/`*_responses.rs` headers state adapters are not wired. Legacy `thrift_matching.rs` is the active real request path.
- Native gRPC service implementation is absent from this crate's production sources: repository search found `NativeMatchingApi` implemented only for forwarding adapters (`matching_forward_native.rs`) and test fakes; `matching_dispatch_native::NativeMatchingApi` is a narrower dispatcher-facing interface, not the generated tonic service trait. Do not treat the internal forward service test server as the Matching listener.
- Existing Rust `Matching` path, adapters, comments, and in-module tests are source evidence only. No build, tests, SDK gate, mixed-cluster run, failure/restart/recovery validation, or parity audit was run for this note.

## Integration order

1. Complete native storage selection and a native runtime owner for `NativeQueueRegistry`, including configured persistence, domain cache/hooks and shutdown/maintenance lifecycle.
2. Build explicit byte-preserving adapters for membership/shard ownership, local/parent routing, partition refresh, scaler callbacks, live dynamic config, metrics/poll observers and fatal sinks; attach them during runtime construction.
3. Implement native Matching RPC handler methods atop native registry/domain/history paths, preserving arbitrary string bytes in requests, keys, routing decisions and errors.
4. Switch production tonic listener registration to native generated Matching server wrapped in `RawStatusService`; retain proper metadata/health registration and note the wrapper's unary-only boundary.
5. Switch production Thrift dispatch transport to native request/response adapters and handler; complete unsupported nested/event decoding before enabling those paths.
6. Only then run parent-owned CI and mixed Go/Rust compatibility/failure/restart/recovery gates; record workflow URL, head SHA, conclusion and binary SHA where applicable in evidence.
