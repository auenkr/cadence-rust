Cassandra task rows multiplex task and task-list rows in the `tasks` table, partitioned by `(domain_id, task_list_name, task_list_type)`. Row `type=0` is a task; `type=1, task_id=-12345` is the task-list lease. Go task UDT fields are `domain_id`, `workflow_id`, `run_id`, `schedule_id`, `created_time`, and `partition_config`. The task-list UDT fields are `domain_id`, `name`, `type`, `ack_level`, `kind`, `last_updated`, and `adaptive_partition_config`; the latter includes nested read/write partition maps in current schema. Go batches task inserts with a conditional range-id update, so any Rust implementation must preserve the logged conditional batch atomicity and TTL behavior.

Go domain lookup reads `domains_by_name_v2` (partition 0) for the nested `domain`, `config`, and `replication_config` UDTs and notification/version columns; it also relies on `domains` for the UUID-to-domain mapping. The domain config UDT includes retention, emit metrics, archival settings, bad binaries, isolation groups, and async workflow config blobs/encodings. Replication includes active cluster, clusters, and active-cluster config blobs.

Source-only audit addendum (2026-10-20; still unvalidated):

- `nosqlTaskStore.CreateTasks` computes `Expiry - currentTimeStamp` in whole seconds, drops rows whose nonzero expiry is already reached, and gives each accepted row the same fresh `CreatedTime`; `CDB.InsertTasks` omits TTL for nonpositive values and caps positive values at `630720000`. The Cassandra adapter's `task_not_expired` check is aligned when queue writers call `at_creation` before persistence. Its `task_ttl` uses the same second truncation and cap. The just-added filter is covered by source unit assertions only. Empty batches still need a semantics test: the Rust adapter substitutes the stored list `last_updated_nanos` for Go's request `CurrentTimeStamp`, so the task-list fence timestamp can differ even though both fence the same range.
- Rust `task_list_lwt_applied` decodes a fixed 11-column tuple for every conditional result. Cassandra `[applied]` results can have a different result metadata shape by statement/table and success/failure path; verify actual Scylla/Cassandra driver decoding before relying on this decoder. The lease insert and list updates also use it. No database or driver validation has been run.
- Domain enumeration in Go passes Cassandra driver `PageState` and `PageSize` through unchanged. Rust emits a UTF-8 last-domain-name token and resumes with `name > ?`; this token is deliberately Rust-internal and cannot resume an opaque Go Cassandra page token. Confirm the Matching domain-cache caller treats page tokens opaquely and add a mixed-seed test for the sentinel `cadence-domain-metadata` at page boundaries.
- Panic/error robustness: persistence conversion paths generally return errors, but `nanos(DateTime)` silently maps unsupported nanosecond ranges to zero. The task listing cast `batch_size as i32` can wrap for values above `i32::MAX`; clamp or reject before query. `complete_tasks_less_than` issues one DELETE per selected task after a bounded SELECT, so a mid-loop error leaves a partially completed batch unlike Go's single range DELETE; audit whether callers depend on atomicity.
- Reproducible validation remains unrun by instruction. Once the build lane is granted, use a Cassandra instance with the pinned Go schema and Go `CDB` as oracle: Go creates/updates the task-list row and seeds regular, expiring, expired, sticky, and adaptive-partition tasks; Rust opens the same store, lists tasks across page/batch boundaries, completes a bounded interval, performs lease/update and restart/recovery; then Go reopens to check task IDs, UDT fields, TTL/remaining expiry, row types, range ID, sticky TTL, and metadata notification version. Also run Rust writes then Go reads, stale-range atomic rollback, empty task batch, mixed expired/unexpired batch, and metadata sentinel on page boundary. Run with only Rust Matching replacing Go Matching while Go Frontend/History/Worker remain up, then drive existing SDK workflow/activity and include service restart/recovery. Capture exact commands, schema/Cassandra version, logs, and Go assertions under `memory/evidence/`; do not mark service complete based on adapter-only checks.
- Another concrete parity mismatch: Go `RangeDeleteTasks` ignores `BatchSize` and executes one range DELETE for all task IDs in `(MinTaskID, MaxTaskID]` (the nosql store supplies `MinTaskID=0` for GC). Rust currently selects at most `limit` IDs and deletes them individually, returning a count; this can leave acknowledged tasks behind for a pass and can partially delete on error. Match the exact service contract or document the intentional queue-level repeated-GC behavior with an integration test before claiming parity.
