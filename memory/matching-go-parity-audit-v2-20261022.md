# Matching Go/Rust parity audit v2 (2026-10-22)

## Scope and evidence rules

This is a source audit of the committed integration branch `origin/t3/matching-integration-20261021`, checked out at `f17c25d95` (merge commit `Merge origin/matching-metrics-gaps-20261021 into integration`). It rechecks the prior report at `origin/audit/matching-go-parity-20261021:memory/matching-go-parity-audit-20261021.md`; that report's `master` baseline is stale. Paths and line numbers below refer to this integration branch. No build, test, server launch, or Go run was performed. “Implemented” means a production code path is present; it is not runtime compatibility evidence. This report does not establish mixed-cluster, SDK, failover, restart, or recovery behavior.

The status labels are `implemented`, `partial`, `missing`, and `different`. A row is `different` where source inspection finds a concrete behavior mismatch; `partial` means there is a production implementation but other Go behavior/dependencies remain absent or unverified.

## Production path and previously stale findings

* Production selects `MatchingRuntime` from the configured `persistence.defaultStore` (`rust/crates/cadence-server/src/main.rs:1194-1268`). Explicit production configuration calls `open_configured_default_store` (`main.rs:1135-1172`), attaches a shared domain cache (`:1174-1193`), and constructs the durable runtime (`:1204-1224`). In-memory Matching remains a development or fallback mode (`:1225-1268`, `:1353-1356`).
* Production binds Matching gRPC and TChannel listeners before membership bootstrap (`main.rs:997-1021`), constructs a `MatchingRingpopProvider` from `cfg.ringpop` (`:1013-1023`), attaches a live Membership object to the runtime (`:1043-1058`, `:1291-1294`), and starts membership before serving the cluster (`:1362-1394`). This supersedes the old audit's claim that Ringpop and Membership were only test helpers.
* When `shard-distributor-matching.namespaces` is configured, production creates the outbound shard-distributor channel, metadata, dynamic onboarding/exclusion properties and calls `MatchingRuntime::with_shard_distributor` (`main.rs:1296-1351`). The runtime starts the executor and spectator and attaches shard ownership checks and queue ownership policy (`rust/crates/cadence-server/src/matching_runtime.rs:232-339`). `matching_shard_processor.rs` is committed on this branch and provides the QueueRegistry-backed processor (`:17-123`). This supersedes the old “unreferenced / missing processor” findings.
* Matching persistence is no longer SQLite-only. `open_configured_default_store` supports SQLite, MySQL, PostgreSQL and Cassandra (`rust/crates/cadence-server/src/matching_task_store.rs:132-293`). MySQL and PostgreSQL map `useMultipleDatabases` and `multipleDatabasesConfig` into physical shards (`:184-228`, `:238-288`); SQLite explicitly rejects multi-database configuration (`:172-182`). Cassandra gets its own adapter (`:144-167`). It remains a bounded port of Go's stores/configuration, not proof every driver option and operational failure mode matches.
* Production starts a Matching metrics runtime from service config, passes the sink to Matching and persistence, and flushes it at shutdown (`main.rs:973-995`, `:1272-1276`, `:1631-1635`). Exporters exist for StatsD, M3 and Prometheus (`matching_metrics_runtime.rs:12-16,24-100`). The emitter's metric catalog and coverage remain incomplete (see below); this corrects the old claim that Matching had no metrics exporter/emitter.

## Metrics

Go Matching emits service metrics and RPC scopes through the common metrics client (`go/service/matching/service.go:100-120`; handler scopes, e.g. `handler.go:252-292`; definitions in `go/common/metrics/defs.go:1503-1538,3058-3154`). Rust's new emitter defines Matching events in `matching_metrics.rs:73-200`, and handlers/queue components emit request, poll, query, forwarding, scaler, persistence and quota events (for example `grpc_matching.rs:3057-3074`, `matching_dispatch.rs:527-586,966-1051`, `matching_metrics.rs:202-248`). Exporters/config are StatsD, M3, Prometheus (`matching_metrics_runtime.rs:12-16,24-127`; config `config.rs:55-92`).

Status: **partial**. Exporter transports and service-level sink wiring exist, unlike the stale audit's “no metrics” conclusion. The Rust event set does not establish equivalence to every Go metric name, scope, tag, histogram bucket, RPC outcome, throttled log or membership/shard-distributor metric; compare `defs.go` and every Go emission path systematically. PProf is configured per service (`config.rs:567-573`) and is passed into metrics initialization (`main.rs:973-985`), but its operational endpoint parity also needs verification.

## Health and admin endpoints

* Go Matching's `handler.Health` waits for handler start and returns `Ok` with `matching good` (`go/service/matching/handler/handler.go:89-111`); gRPC registers Meta health (`wrappers/grpc/grpc_handler.go:35-42`), and Thrift registers Meta health (`wrappers/thrift/thrift_handler.go:45-52`).
* Rust Thrift dispatches `Meta::health` to shared YARPC health (`rust/crates/cadence-server/src/thrift_matching.rs:695-699`); shared gRPC Meta health returns `ok: true` unconditionally (`grpc.rs:325-335`). The HTTP `/health` endpoint is shared (`handlers.rs:237-242,813-820`). There is no Matching-start readiness gate corresponding to Go's handler start wait.
* Matching's Go service registers Matching and Meta endpoints; admin RPCs are not registered by that Matching wrapper (`go/service/matching/wrappers/thrift/thrift_handler.go:45-48`; gRPC `:35-38`). Rust's `/api/v1/admin/...` HTTP routes are shared server admin/frontend routes (`handlers.rs:900-1040`), not a Matching-specific Thrift admin surface. Status: **partial** for Meta health readiness and **different** for HTTP admin surface/ownership; no claim that admin API parity belongs to the Matching transport contract.
