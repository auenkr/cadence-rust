# Cross-review of Codex findings C1-C9 (Opus, read-only), master 3ace896eb, 2026-11-04

Static code reading only. No builds or runs. Paths are relative to `rust/crates/`.

| ID | Verdict | Severity | Evidence / notes |
|----|---------|----------|------------------|
| C1 | AGREE (duplicate of O10) | high | `cadence-proto/src/convert/mod.rs:382` computes `seconds*1000 + nanos/1e6` (milliseconds). `cadence-frontend/src/workflow_backend.rs:609-614` compares it with `now.as_nanos()`. A future time in ms is always smaller than now in ns, so the delay is lost and the run starts immediately. Go uses `timeToUnixNano`. |
| C2 | AGREE (new) | high | `cadence-frontend/src/workflow_matching.rs:313-314` and `:341-342` divide by `1_000_000`. The value is passed through unchanged at `:464-465`, then sent as `timestamp_nanos` (`convert/mod.rs:294-295`) and as raw Thrift i64. No other code multiplies it back. As a result, SDKs see scheduled/started times near 1970 on every decision poll. Go copies the nanoseconds unchanged. |
| C3 | AGREE | high | `cadence-matching/src/grpc.rs:499-502` drops the thrift value (`let (name, _, message)`). `status_from_error_type` (`grpc.rs:93-135`) maps AlreadyStarted, DomainNotActive, ClientVersionNotSupported and CancellationAlreadyRequested to bare codes with no detail. ServiceBusy gets an empty `reason`, and EntityNotExists gets a default detail with no cluster fields. Go SDK `errors.go` mappers need the AlreadyStarted detail (and its RunId) to build `WorkflowExecutionAlreadyStartedError`. |
| C4 | AGREE | high | The `with_poll_admission` builder is at `cadence-frontend/src/handler_workflow.rs:787`. No production call site exists; a repo-wide grep finds only the definition and tests. The factory in `workflow_backend.rs` does not install it, so bad binaries are never rejected. |
| C5 | AGREE | high | `workflow_backend.rs:780-787` builds `CallerMetadata` with `..Default::default()`, so `isolation_group` is always `""`, and `cadence-client-isolation-group` is never read. `with_isolation_group_state` and `with_poll_isolation_waiter` (`handler_workflow.rs:782`, `:792`) are never installed in production. No `partition_config` is encoded in History start envelopes (grep in cadence-frontend finds nothing). The drained-group logic at `handler_workflow.rs:1205`, `:1297` and `:1706` is unreachable in production. Severity is high only for deployments that use isolation groups; otherwise it has no effect. |
| C6 | AGREE | medium | `with_outstanding_poll_canceller` (`handler_workflow.rs:806`) is never called outside tests. Medium is the right severity: polls expire on their own timeout, but tasks matched to a poller that has disconnected are delayed until they time out. |
| C7 | AGREE | high (medium if no active-active domains) | `convert/mod.rs:345-349` returns `UNIMPLEMENTED` for any `active_cluster_selection_policy`. It also overlaps with O14 (the field is missing from the API models). Go SDKs only set this field when the user configures it, so the impact is limited to active-active users. Because the request is hard-rejected, severity stays high for them. |
| C8 | AGREE | medium | `cadence-api/src/tasks.rs` and `convert/mod.rs` contain no `auto_config_hint` or `total_history_bytes`. The decision response falls through to `..Default::default()` (`convert/mod.rs:315`). SDK poller autoscaling and history-size checks see zero or none. |
| C9 | AGREE | medium (low in default configs) | `workflow_matching.rs:431` hardcodes `HISTORY_MAX_PAGE_SIZE` (1000). The `with_history_page_size_policy` policy (`workflow_backend.rs:1418`) is only consulted in GetHistory (`:780-782`). The Go default is also 1000, so behaviour differs only when a domain overrides it. |

## Summary
- I agree with all 9 findings. C1 duplicates O10. C7 overlaps with O14. C2, C3, C4, C5, C6, C8 and C9 are new compared with O1-O38.
- Highest-impact items for SDK compatibility are C2 (affects every decision poll), C1, and C3 (AlreadyStarted error detail, which SDKs commonly rely on).
- C4, C5 and C6 share one root cause: the factory never installs the optional handler hooks. A single fix in `build_workflow_api` covers all three, but each still needs its own production implementation.
