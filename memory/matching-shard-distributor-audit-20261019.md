# Matching shard-distributor ownership audit (2026-10-19)

Source-only comparison of Go Matching's shard-distributor executor/resolver wiring and the current Rust Matching runtime. No build or test was run. This is the follow-up to the production gap checklist in `matching-production-gap-audit-20261018.md`.

## Finding: configured Matching namespace path is entirely absent in Rust

Rust does implement the shard-distributor **server** (`grpc_shard.rs`, registered in `grpc.rs`) and its generated protobuf APIs exist (`rust/proto/shard-manager/...`). That server-side implementation does not provide Matching's outbound shard-distributor executor/spectator clients. `cadence-server::Config` has no `shardDistributorClient` or `shard-distributor-matching` fields (`rust/crates/cadence-server/src/config.rs:14-36`); serde structs do not deny unknown fields, so those YAML sections are silently ignored. `main.rs` constructs Matching and optionally a durable SQLite queue but never reads namespace config, constructs executor/spectator clients, or supplies a shard processor factory (`main.rs:730-786`). The proto crate exposes generated server/client code, but no outbound client/runtime use was found. Therefore a configured Go Matching namespace cannot currently activate the Rust executor/ownership path at all.

The Rust local Ringpop membership gate is a separate, partial ownership mechanism: `QueueRegistry::get` calls `Membership::check_task_list` if a provider was supplied (`matching_registry.rs:684`), and `unload_non_owned` tears down moved owners. `Matching::with_membership` wires that provider (`grpc_matching.rs:802-805`), but the production main path has no call to `with_membership`; the API is currently opt-in. This does not implement shard-manager assignment.

## Go behavior to preserve

- Service setup injects `ShardDistributorExecutorClient`, `ShardDistributorMatchingConfig`, percentage-onboarded, listener config and drain observer into Matching (`go/service/matching/service.go:85-120`; engine constructor `engine.go:157-194`). `Start` starts the executor and registers domain callbacks; `Stop` stops it before managers and unregisters callbacks (`engine.go:200-218`).
- `setupExecutor` uses a no-op executor only when `Namespaces` is empty and still installs a shard-processor factory with a 1-minute default report TTL. With namespaces present it permits at most one, uses configured nonzero `TTLReport` or the same 1-minute default, advertises TChannel port, gRPC port and listen IP, and supplies the executor client, metrics, clock, factory, onboarding callback and drain observer (`engine.go:221-316`). Bad namespace cardinality and executor construction failures are fatal startup errors.
- Manager creation checks shard-manager assignment before reuse/creation. Excluded task-list names bypass the executor and must be owned by the local Matching hash ring. Eligible names use `GetShardProcess`; a local processor permits reuse, while absent/not-assigned ownership yields typed TaskListNotOwnedByHost, and other lookup errors remain operational errors (`engine.go:317-355,1600-1650`). Exclusion is a deterministic Farm fingerprint modulo 100 against the live onboarding percentage, or a UUID-containing short-lived name when that feature is enabled (`common/membership/tasklist_differentiator.go:13-31`; `engine.go:1703-1705`).
- The separate Membership resolver wraps Matching's hash ring with a spectator only when outbound SD client and namespace config exist. Excluded/unonboarded keys use the ring; eligible keys use SD; missing spectator falls back to ring. `LookupN` and subscriptions remain ring-based (`go/cmd/server/cadence/server.go:165-207,305-345`; `common/membership/sharddistributorresolver.go:58-110`). The spectator is onboarding-gated and namespace-specific.
- Executor heartbeats/assignments drive processor lifecycle. The external client is `github.com/cadence-workflow/shard-manager` pinned in `go/go.mod`; executor Heartbeat is a separate API from spectator lookups. Rust's same-named shard-distributor server API is not a substitute.

## Bounded implementation plan

1. Add Go-shaped typed config parsing for `shardDistributorClient.hostPort`, matching executor `shard-distributor-matching` namespace config, report TTL and related executor fields. Validate namespace count and invalid combinations at startup; do not silently accept configured namespaces without a client. Add config fixtures proving zero/one/multiple namespace handling and no-namespace default.
2. Add Rust outbound gRPC executor and spectator adapters using the pinned shard-manager protobufs. Match timeout/retry policy, namespace addressing, heartbeat cadence/status, executor identity/metadata, assignment application, TTL, and graceful drain/stop. Build a shard-processor factory that owns/starts/stops Matching task-list processors from assignments.
3. Add a live ownership policy at `QueueRegistry::get` and owner reuse: deterministic onboarding percentage and optional short-lived UUID exclusion; excluded lists use Ringpop ownership; eligible lists require local SD assignment and preserve Go typed ownership vs transient lookup errors. Do not conflate this with hash-ring partition/scaler state.
4. Wire Matching startup/shutdown in `main.rs`: provide listener IP/ports and drain observer, start executor/spectator under configured namespace, stop/drain and join them. Separately finish the existing Ringpop membership startup wiring so the fallback route is real.
5. Verify with source-derived Go oracle cases for assignment/no-assignment/error, onboarding percentage bucket boundaries and stable hashes, UUID exclusion, namespace validation/default TTL, metadata, processor start/stop, drain, restart/reassignment, and eligible-vs-excluded routing. Then run mixed Go Frontend/History/Worker + Rust Matching with no Go Matching, including remote SD failure and owner movement/recovery.

Keep this as Matching work; do not begin History migration. The plan above does not claim implementation or validation.
