# Matching native ack / GC configuration audit — 2026-10-29

Base reviewed `530953ac72fa906d23df3247bed2ba2531b2c03d`, merged into this branch. Static inspection only. No Cargo, Go, runtime, formatting, Actions dispatch or polling performed.

* `UpdateAckInterval`: `matching.updateAckInterval`, 60s, domain name/task-list name/task type filters (`go/common/dynamicconfig/dynamicproperties/constants.go`, `go/service/matching/config/config.go`). `newTaskListConfig` binds names at construction; `task_reader.go::getTasksPump` samples at timer creation and after each completed ack update. Go durations are signed i64 nanoseconds, parsed using `time.ParseDuration` for file config; invalid values fall back to default. Nonpositive Go timers fire immediately. Configured native assembly (`matching_launch_native.rs::assemble_configured`, `matching_runtime_native.rs::{native_queue_registry,reader_properties_provider}`) installs filtered live providers; `matching_reader_native.rs` and `matching_registry_native.rs` each sample on creation/reset. Native previously clamped nonpositive values to 1ns; changed both native timers to zero. Positive values through i64::MAX remain representable. **Not equivalent overall:** Go persists ack and signals the pump in the same reader select, after any blocked read/buffer operation; native registry `maintain_until/flush` persists on a separate timer while native reader timer merely wakes its scan. Native registry resolves domain name on each provider call while Go binds it; reader captures name. This lifecycle/sampling discrepancy remains unresolved and requires integration work; condition-failure and shutdown ordering need a focused regression when corrected. Native reader's scan-pending and read-error paths also skip its timer select. No parity claim.
* `MaxTimeBetweenTaskDeletes`: fixed `time.Second`, no dynamic key or filters; copied to task-list config at construction. `task_gc.go::tryDeleteNextBatch/checkPrecond` compares `time.Since(lastDeleteTime) > interval`, first attempt starts with Go zero time, and only checks time after positive backlog when size threshold did not pass; force bypasses time, not backlog condition. Configured native `matching_registry_native.rs::build_owner` constructs `DurableTaskQueueBytes`; `matching_native_queue.rs::run_garbage_collection` passes fixed one second to `matching_gc.rs::run_with_batch_provider`, using absent last-delete as immediately elapsed. Native GC is called on completion and forced on `Owner::finish`; Go reader calls Run on ack and RunNow on Stop. Fixed production value is positive and representable; arbitrary negative duration is not a production setting and Rust Duration cannot represent it. Threshold, first attempt, attempt-time update on error and shutdown force align at source level, subject to lifecycle ordering noted above.
* `MaxTaskDeleteBatchSize`: `matching.maxTaskDeleteBatchSize`, 100, domain name/task-list name/task type filters. Go binds identity in `newTaskListConfig` and samples signed machine `int` after GC try-lock on each invocation, once for whole drain; native `integer_provider`, `build_owner`, `matching_native_queue.rs`, `matching_gc.rs` do the same with signed i64 on this 64-bit target, except native resolves domain name per call rather than binding it. Invalid/noninteger config defaults; no positive clamp. Backlog uses wrapping signed subtraction and `>= batch`, loops until returned count < batch, updates cursor only then; errors end the attempt without moving cursor. Zero/negative batches can cause repeated deletes indefinitely when backend returns a nonnegative count; do not silently clamp. SQL backends may reject limits (e.g. native PostgreSQL explicitly rejects zero); Cassandra ignores limit and returns zero. Backend-specific edge parity is not established by this audit. Sampling identity mismatch remains unresolved. `matching_gc.rs` bounded tests cover signed batches via injected terminating errors and threshold/lock behavior; they do not assert an unbounded loop.
