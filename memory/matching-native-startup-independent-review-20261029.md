## Proved source defects, causation unproved

1. **Cold domain lookup can recursively lock the overlay.** `matching_runtime_native.rs:integer_provider` (around 461), `duration_provider`, `boolean_provider`, `writer_live` and standby provider take `state.admin.dynamic_config`'s non-reentrant mutex and then call their locally named `cached_domain_name`, which is actually read-through: `domain_by_raw_id` calls `MatchingDomainCache::get_domain_by_id` (`matching_domain_cache.rs:847`). On a miss, `RateLimitedDomainSource::call` (`matching_persistence.rs:248`) invokes `MatchingPersistenceLimiter::allow` (`matching_persistence_limiter.rs:594`), which when enabled and its refresh interval has elapsed holds the limiter state and calls `read_rate_snapshot`, attempting the same overlay mutex. The same thread cannot release it; this is a deterministic deadlock under those conditions. There is also a possible two-thread inversion: the first thread holds overlay and awaits limiter state while a concurrent limiter refresh holds state and awaits overlay. A cache hit or disabled/not-yet-due limiter avoids this particular cycle. I did not establish that any of these providers is invoked during initial native assembly, so this is **not a demonstrated cause** of run 40808511931. `record_started_timeout_provider` already resolves the name before taking overlay; apply that ordering consistently while preserving read-through behavior, and ensure no caller holds overlay across a persistence lookup. Regression: cold valid ID, production limited source, enabled limiter with controlled clock advanced past refresh, invoke each provider on a bounded blocking thread; assert completion and values, also orchestrate a concurrent limiter refresh. Use CI only.

2. **PostgreSQL pool fails to wake waiters when a healthy lease becomes idle.** `matching_postgres.rs:PostgresLease::drop` lines 245-269 calls `available.notify_one()` only on discard, not on `state.idle.push`. A waiter in `checkout_until` (lines 135-215) can remain asleep while a usable connection is idle; unbounded `checkout()` can wait indefinitely absent another notification, while a timed `checkout_with_timeout` waits until its deadline and then can acquire the idle lease. Notify after every returned lease, preferably after releasing the pool mutex. Regression: max_open=1, hold one lease, start a second checkout and establish it is waiting, return the first healthy lease, assert the second completes well before a long timeout; also cover unbounded checkout and discard. CI PostgreSQL test must verify the actual pool. This bug is not by itself proof of the observed hang: initial metadata and page calls use separate scoped leases (`matching_domain_postgres.rs:54-75,143-193`), and `connect_with_domain_metadata` explicitly drops the schema-validation lease (`matching_postgres.rs:330-361`). No nested checkout is evident there. New connection establishment is performed outside the pool lock, but `checkout_with_timeout` does not itself enforce its deadline across `options.connect`; transaction establishment and network I/O may also outlive the SQL statement timeout. Instrument actual durations before assuming a three-second wall-clock bound.

## Ranked startup hypotheses and discriminating evidence

1. **Cache initial refresh or callback registration is blocked** (highest priority to locate, not proven). `launcher.rs:1216-1304` opens the configured store on `spawn_blocking`, attaches the shared limiter and cache; `matching_launch_native.rs:assemble_configured` -> `assemble` -> `MatchingRuntime::in_memory_with_domain_cache` -> `start_domain_cache` (`matching_runtime.rs:866-1005`) awaits another `spawn_blocking`. `cache.start` synchronously runs `refresh_domains` under `refresh_lock`, with metadata then paginated ListDomains through the limiter. `register_callback` also holds `refresh_lock` across catch-up. The catch-up writes the version under a short statement-scoped guard before `changed` reacquires it; it is not an unconditional recursive lock. Initial `changed` has no native registry yet. `with_domain_cache` on the limiter installs a weak resolver using snapshot-only `cached_domain_name`, so this attachment itself is not a recursive persistence call. No source proof that initial refresh self-deadlocks was found. Instrument flushed, timestamped enter/exit/error markers around store open, `assemble_configured`, cache start, metadata/list each page (including limiter entry/exit, pool checkout, transaction/query and lease return), registration and catch-up; include elapsed times, thread IDs, and page number, without domain data. Capture thread stacks on timeout. This locates the block instead of inferring it from generic integer logs. Avoid holding instrumentation locks across callbacks.

2. **Ringpop bootstrap or lifecycle after assembly** remains an independent alternative. The shared TChannel task is spawned only at `launcher.rs:1520-1545`, immediately before `MatchingMembershipLifecycle::start` in the `tokio::select!` at 1549. Lifecycle start awaits provider start, subscribe, then initial refresh (`matching_membership_lifecycle.rs:50`). `MatchingRingpopProvider::start` holds its async lifecycle mutex while discovering seeds and awaiting `join_cluster` (`matching_ringpop_provider.rs:229-268`). `join_cluster` checks its maximum only after `join_group` finishes; `join_group` waits for every spawned JOIN; each `join_seed_signed` supplies its configured timeout to the TChannel JSON call (`ringpop_provider.rs:216,1120,1272`). Therefore a configured group or transport operation that does not complete as expected can postpone the outer maximum; source alone does not establish it happened here. Add markers for shared listener task actually entering accept loop, resolved seeds, JOIN target/timeout, completion/error per target, group result, provider start, subscribe, initial membership snapshot and mark_started; capture Go/Rust membership snapshots and bounded connection/stack evidence. Verify configured duration and whole-call timeout semantics in the transport, including connect and response, before altering retry behavior. Existing signal selection covers the bootstrap phase, but pre-bootstrap `spawn_blocking` awaits occur before that selection; a stuck blocking task can prevent orderly shutdown. Add a configured-start cancellation regression that verifies process termination with a deliberately blocked source; cancellation of a Tokio blocking task alone does not stop its underlying synchronous operation.

3. **Other pre-listener assembly** (store opening, native registry, shard-distributor setup) is possible until staged markers identify the last completed operation. In particular a real configured shard distributor may await setup at `launcher.rs:1457-1503`. Record the effective branch and component boundaries rather than claiming cache or JOIN solely from log order. Two fallback messages are emitted by generic dynamic integer readers at many sites; they do not identify a unique stage.

## Why the assembly test does not exclude these paths

`matching_launch_native.rs::tests::configured_service_gates_admission_and_stops` supplies `EmptySource` with immediate metadata/list returns, no production persistence limiter, in-memory semaphore, SQLite task store and synthetic membership. It checks admission gating after `assemble_configured`; it neither opens the PostgreSQL shared pool nor runs launcher listener/bootstrap or a real Go peer. It therefore cannot exercise pool lease contention, limited cold domain read-through, configured discovery/JOIN, or process signal behavior during an indefinitely blocked startup. Add focused deterministic regressions above, then rerun the actual native mixed PostgreSQL gate with stage evidence and binary SHA on a newly validated immutable candidate. No service-completion credit follows from these tests alone.
