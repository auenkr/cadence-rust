## Common evidence required for every mixed lane

Use the lane's complete uploaded `out/` tree. Verify Actions `headSha`, `out/commit.txt`, and frozen `FINAL_SHA` agree; retain `out/binary.sha256` and check it identifies the executable passed to the harness (not just a build product with the same filename). Require successful build, gate, nested `run.exit`, `results.json` result, and probe outcome. `out/command.txt`, `results.json`, `binaries.json` where emitted, captured configs/config hashes, and Rust/Go service logs establish the actual invocation and process identity. The running topology must show one Rust Matching plus the original Go Frontend, History and Worker, with no Go Matching. Retain Go SDK logs and the final visible workflow/history result; for lanes requesting restart or recovery, inspect the corresponding workflow completion and process/owner transitions. The common TLS workflow requests graceful drain/restart and two-instance failure recovery; production-validation Thrift, Configstore and shard-distributor lanes request restart, two-instance recovery, and idle recovery. Require their actual scenario outputs, not just flags or a green job. Inspect MySQL/etcd/container cleanup records and process teardown. Missing identity, topology, outcomes, or cleanup leaves the lane uncredited.

## Thrift and TChannel lane

Workflow: `.github/workflows/matching-production-validation.yml`, lane `thrift`; it runs `--matching-transport thrift --history-transport tchannel --probe-auto-config-hint` with the common restart, failure-recovery and idle checks. Inspect `out/command.txt`, nested `out/gate/run/results.json`, `run.exit`, `probe.log`, Rust Matching logs, and Go service logs. Require results to identify Matching's Thrift transport and History's TChannel transport, then inspect the SDK workflow outcome and service call evidence. The caller configuration in `tests/run-go-service-baseline.py` constructs the original Go services against Rust Matching for this mode; acceptance depends on completed RPC/workflow behavior through that running path, not the transport option text alone. The restart and recovery checks must show recovered work completing once and idle recovery completing, as reported by results/probe logs.

Evidence limitation: this lane exercises real mixed service workflows; its artifacts do not by themselves establish exhaustive coverage of every generated Thrift method or TChannel method. Do not expand the lane's claim beyond the recorded calls.

## Configstore provider lane

Workflow lane `configstore` selects `--matching-configstore` (MySQL wrapper). Inspect the configstore seed helper invocation/binary identity, seed log or captured row/config, effective Rust Matching configuration, `results.json` `configstore` object, `probe.log`, and SDK/service logs. The concrete required assertion is that the Go helper seeds `matching.longPollExpirationInterval` as a 2-second value in Go's `cluster_config`, and an empty direct Matching poll returns empty after approximately that interval rather than hitting the default 60-second expiry. The source assertion records seeded expected interval, measured elapsed time and owner and rejects a returned task. Also require common SDK, restart, two-instance failure recovery, idle recovery, topology, exact binary identity and cleanup proof.

Evidence limitation: this verifies application of the seeded long-poll setting through the configured provider in this fixture. It does not establish every Configstore key, precedence rule, live update, or provider failure behavior; the artifact must retain the specific seed and measured poll evidence to support even the bounded claim.

## Shard-distributor discovery lane

Production lane `shard-distributor` passes `--real-shard-distributor`, whose documented fixture is the real Go shard-distributor fx/leader loop with a single-node etcd container and ephemeral `matching` namespace (see `tests/run-go-service-baseline.py` help and `tests/run-matching-shard-distributor-production.py`). This is distinct from the in-memory handler fixture and must not be described as multi-node etcd validation. Inspect fixture startup/identity, etcd and shard-distributor logs, executor stats/assignments snapshots, Rust Matching registration/heartbeat logs, shard task-list owner/READY evidence and the gate's `results.json` `shardDistributor` entries.

Required assertion sequence is an actual assignment to the selected Rust executor; after that exact executor is SIGKILLed, its heartbeat expires within the asserted 90-second bound, its executor record and assignments disappear, and surviving/restarted Rust Matching re-registers and can obtain ownership again. Restart checks must show fixture restart with empty state followed by Rust heartbeat/re-registration and a successful task-list operation. Preserve selected executor IDs and metadata plus before/after heartbeat and assignments so expiration/removal cannot be attributed to another node. The current probe enforces deterministic metadata-to-port selection and fails on lingering executor/assignment; if timeout occurs it writes a diagnostic JSON snapshot. Require the fixture stop and runner-owned etcd cleanup record.

Evidence limitation: scope is the configured single-node etcd fixture and its real leader loop/heartbeat TTL; this is not a production multi-node shard-distributor topology. The old handler-only/interoperability test and `acceptanceEligible` metadata are not substitutes for the production lane's TTL/removal/recovery outcomes.

## Production TLS mixed lane

Workflow: `.github/workflows/matching-production-tls-mixed.yml`, which invokes the MySQL mixed harness with `--matching-rpc-tls`, restart and two-instance failure recovery. Inspect the harness command, `results.json`, Rust and Go logs, binary identity, and redacted generated configurations. The executable assertion setup is in `tests/run-go-service-baseline.py`: it creates a per-run CA and server certificate with `DNS:localhost` and `IP:127.0.0.1` SANs; configures Go's outbound Matching client with that CA, `enableHostVerification: true`, and `serverName: localhost`; and configures the Rust Matching gRPC listener with the generated server certificate/key. A qualifying run must show completed Go service-to-Rust Matching RPC/workflow calls over that configured trust path and the common SDK/drain/restart/failure-recovery outcomes. TLS flags or config fields without successful verified calls are insufficient.

Evidence limitation / confirmed collector gap: current TLS mixed workflow uploads `out/` while excluding generated executables, but the generic `matching_evidence.py` redaction masks `caFile`, certificate/key and `serverName` values, and the baseline's generated TLS material lives under its temporary config directory. The workflow does not explicitly retain a safe TLS evidence bundle (CA/server certificate public fingerprints or SAN/issuer inspection, redacted effective TLS config plus hashes, and proof/log of a successful verified client call). Thus source code proves the harness is designed to require hostname verification, but the lane artifact as configured may prove only that TLS was requested and the scenario passed; it may not independently prove which certificate/config the running processes used or hostname verification was active. Do not credit this lane's TLS-specific claim without retained runtime evidence tying effective configs and the running binary to a successful verified transport. Preserve no private keys or passwords.
