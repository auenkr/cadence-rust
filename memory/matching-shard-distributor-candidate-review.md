## Source findings

- `TonicSpectator::get_shard_owner` caps its 10-second per-RPC ceiling by the caller's remaining deadline. Go Matching's resolver passes a 1-second context (`go/common/membership/sharddistributorresolver.go:136-140`), so this layer preserves the effective 1-second resolver bound.
- Go resolver metadata mapping is still an integration requirement: `hostIP` is mandatory; `tchannel` and `grpc` parse as unsigned 16-bit decimal values; absent/invalid ports are omitted, and the host address uses TChannel port or zero. Executor ID is the host identity.
- `ShardDistributorMatchingConfig::report_ttl_nanos()` (`config.rs:96`) provides Go's one-minute default, but `ShardDistributorExecutor::new` (`matching_shard_distributor.rs:553`) does not consume report TTL; its `ttl_shard` drives idle shard status. The runtime-owned `ShardProcessorFactory` (`matching_shard_distributor.rs:59`) must capture the report TTL when constructing processors.
- Processor callbacks stay caller-owned: the runtime must implement `ShardProcessorFactory::create` to bind real Matching queue/task-list lifecycle, `start`, `stop`, status and report to these callbacks. Heartbeat reports are built at `matching_shard_distributor.rs:724`; assignments are applied at `:775`; the executor does not create Matching queue state. Executor shutdown waits for processor-stop tasks before the DRAINING heartbeat and joins background lifecycle tasks.
- Candidate spectator clears the full owner snapshot when onboarding disables and on stream reconnect/termination before retry; initial state is awaited before lookup and cache misses use unary RPC. This is broadly consistent with the resolver's onboarding-gated, namespace-specific spectator contract. Retry/watch timing parity is not established by source comparison alone.
- Config validation enforces at most one namespace, non-empty namespace, positive heartbeat interval, and client hostPort when namespaces are set. Runtime integration must invoke it and supply metadata containing `hostIP`, gRPC and TChannel ports; the standalone constructor accepts metadata from its caller and does not infer listener addresses.

## Validation and limits

`tests/run-shard-distributor-review-gates.sh` first compiles the `cadence-server` library tests with `--no-run`, then runs focused module tests, config tests, strict `cadence-server` Clippy, and the pinned Go Matching resolver tests. The successful serialized run used `CARGO_BUILD_JOBS=1` and the warmed target and is recorded in `memory/evidence/matching-shard-distributor/attempt-20261020T052159Z/` with raw output, exit code, and before/after hashes. It passed 7 SD unit tests, 12 config tests, Clippy, and all selected Go resolver tests. `first-attempt.log` preserves the asynchronous stop assertion race; after confirming pinned Go assignment updates stop asynchronously, the test was fixed to wait for fake stop completion. `second-attempt.log` preserves the strict-Clippy failures; the final changes are behavior-preserving lint rewrites.

The Rust fake-Tonic tests cover spectator snapshots/fallback/shutdown and executor heartbeat/assignment/drain. The Go oracle is the existing resolver suite. These checks do not prove Rust executor/spectator interoperability with a live shard-manager server, actual Matching runtime integration, mixed Go/Rust cluster behavior, failure/restart/recovery, or Matching service parity. Those validations remain required before declaring Matching complete.
