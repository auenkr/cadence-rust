# Matching to History timeout audit

Read-only source trace, 2026-10-19. Go matching wraps only `RecordDecisionTaskStarted` and `RecordActivityTaskStarted` in `backoff.ThrottleRetry` with per-attempt `RecordTaskStartedTimeout` and context expiration (`go/service/matching/handler/engine.go:1471-1528`). `ThrottleRetry.attempt` makes a child context for each attempt; attempt timeout is retryable (`go/common/backoff/retry.go:176-195,268-287`). The retry expiration is `NoInterval`, bounded by maximum attempts (`go/common/util.go:168-175`). The History client only redirects typed ownership-loss errors and validates caller context; it adds no timeout (`go/client/history/client.go:1160-1188`). Rust's per-attempt deadline for these two calls matches that configured timeout, and redirect attempts share the per-attempt budget. The Rust outer retry should remain the owner of retrying; redirect is only an inner reroute.

Go Matching calls `GetMutableState` directly from query polling (`engine.go:777-788`), `RefreshWorkflowTasks` directly (`engine.go:1531-1550`), and standby `DescribeWorkflowExecution` inside its task-completer retry (`tasklist/task_completer.go:92-120,160`). None passes through a History-client-created deadline; context cancellation/deadline comes from the caller. Go History's five matching RPC wrappers all redirect typed ownership-loss errors only. Therefore Rust's `operation_timeout` in `execute_with_redirect` is an additional local hard deadline for mutable state, describe, and refresh. The previous Rust client already sent `grpc-timeout` metadata for all calls, so `tokio::time::timeout` newly guarantees local future cancellation if the peer/transport fails to honor that header; it does not newly advertise the timeout to a conforming gRPC peer. However, fixed one-second `operation_timeout` still bounds these Go-unbounded caller operations. Preserve caller deadline/cancellation where available; avoid imposing the one-second operation timeout on these three methods unless matching's intended RPC configuration explicitly supplies it.

Go's standby task-completer retry wraps Describe, but no operation timeout is configured there; it retries until its retry policy expires or caller context ends. Rust's standby loop similarly retries around `describe_execution`; a hard one-second per-call timeout makes a slow call into an earlier retryable error. `GetMutableState` is returned to the query requester on failure in Go; Rust's new internal generic retry is also extra relative to Go's History wrapper and should be justified as Matching policy, separate from redirect. Refresh is not retried in Go's caller or History wrapper and entity-not-exists alone is ignored.
