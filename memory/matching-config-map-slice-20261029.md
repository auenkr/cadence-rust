## Independent review of the two persistence QPS fields (2026-10-29)

Reviewed all source changed by `c6853cb35`. **Classification: both fields mismatched in native production**, with the specific differences below; this is not a service parity verdict. The removed negative clamps are correct: after an initially positive limiter is installed, a negative host remains the effective limit even with positive global QPS; Go gives it burst 1, whereas zero has burst 0. The original regression exercises admission after a negative update and would fail with the old host clamp. It now also checks no refill and the zero transition. A negative global rate disables global scaling just as zero does; preserving its raw value is correct, but the old global clamp alone did not change admission. These tests are source-only, not executed.

- **PersistenceMaxQPS**: `go/service/matching/config/config.go:190` binds unfiltered `matching.persistenceMaxQPS`, default 3000 (`go/common/dynamicconfig/dynamicproperties/constants.go:3979`); `common/dynamicconfig/config.go:94` reads on each invocation, defaulting on error. File lookup requires Go `int` and no constrained entry can match an empty filter (`file_based_client.go:107,289`); last unfiltered entry wins. The resource callback passes host and global to `permember.PerMember` (`common/resource/resource_impl.go:202`, `common/quotas/permember/permember.go:32`). Initial effective <=0 omits each datastore limiter permanently; otherwise `factory.go:753` constructs each datastore's bucket, and `dynamicratelimiter.go:67,105,117` samples on construction and first permit at/after five seconds. Later zero cuts burst to zero; negative has burst 1, cannot refill, and can spend retained tokens. Positive rates use ceil with minimum burst 1. On amd64 a host near MaxInt64 rounds to 2^63 as float64; Go's float-to-int conversion produces MinInt and minimum burst 1. The reviewed Rust `burst` had saturated to MaxInt64 instead; corrected in this review with an edge regression. This is an amd64 conversion behavior, not a portable guarantee for other Go architectures.
- **PersistenceGlobalMaxQPS**: `config.go:191` binds unfiltered `matching.persistenceGlobalMaxQPS`, default 0 (`constants.go:3984`), same lookup and sampling. A global <=0, resolver error, or count <1 returns host; otherwise `min(host, max(global/count, 1))` including negative/zero host. Division is floating point. Both keys flow through the same live limiter and consumer, so the discrepancies below apply to both. Global extremes are converted to float64 before division; the effective host bound governs burst.

Native path: configured production `launcher.rs:558-661,719-756,784-805` loads file/config-store snapshots or installs an OpenFeature runtime provider before creating the limiter; `cadence-service-core/src/admin.rs:67-79,188-201` provides ordered snapshot values or typed live reads; `cadence-persistence/src/dynamic_config.rs:265-307,334-336,523-540` selects without filters and defaults invalid/missing values. File/store reload wiring is `launcher.rs:1417-1436` and `matching_runtime.rs` reload tasks. `matching_persistence_limiter.rs:154-183,608-688` samples and computes the rate, initially fixes wrapper enablement, and refreshes on permit; `cadence-common/src/rate_limiter.rs` implements retained tokens and nonpositive refill. `launcher.rs:797-805,1262-1303` attaches its shared limiter to configured task, semaphore and domain-cache stores; native permit calls are in `matching_persistence_native.rs:42,242,258` and `matching_persistence.rs:85,257,416,429`.

Concrete remaining differences: (1) Go resolves the current membership on every rate sample, returning host on resolver error (`membership/resolver.go:241`); native uses an atomic initially zero before the Ringpop provider exists, refreshed once per second from an infallible cached snapshot (`launcher.rs:784,1094-1110`, `matching_ringpop_provider.rs:162,216`). Thus initial and subsequently stale counts can differ, and resolver error is not represented. (2) Go builds a separate limiter per configured datastore (`factory.go:753-762`); native constructs one for the default-store paths, so equivalence for other configured datastores and sampling/enablement at construction is not established. (3) Go config-store integer decoding accepts integral JSON float64 and converts it to int (`configstore/config_store_client.go:197-216`); Rust `integer_value` accepts only JSON `as_i64`. For example, a store value `1.0` is accepted by Go and defaults in Rust; float64 rounding and out-of-range conversion also differ. File and OpenFeature source conversion should be assessed independently, not inferred from that example. (4) Go tests enablement and separately samples when constructing each limiter (`factory.go:757-759`); native uses one snapshot for both (`matching_persistence_limiter.rs:168-173`), so a concurrent update between Go reads can differ. These differences prevent either field being called equivalent despite the corrected negative and amd64 burst behavior.
